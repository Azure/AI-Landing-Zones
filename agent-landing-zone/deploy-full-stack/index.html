    Deploy full stack

    This guide deploys the infrastructure layer and the default application (Agent App UI and Agent App Orchestrator, with an optional Agent App Ingestion Container App) into a new environment with public endpoints. For private networking, read this page and then Network isolation.

    Prerequisites

    For a customer-owned repository and repeatable deployments, use Customer environments and the Azure DevOps walkthrough. The commands below explain the same application lifecycle for an interactive deployment.

    Azure permissions

    • Owner, or Contributor plus User Access Administrator, on the target subscription. The deployment creates role assignments for managed identities.
    • Responsible AI terms accepted for Azure AI services in the subscription.
    • Quota in the target regions for the services and model deployments configured in main.parameters.json.

    Tools

    Tool Notes
    Azure Developer CLI (azd) Latest version
    Azure CLI (az) Used by the lifecycle hooks
    PowerShell 7 Runs Windows hooks and the regional and infrastructure preflight checks on all platforms
    Bash, jq and curl on Linux or macOS Runs the POSIX hooks, parses deployment metadata and bootstraps pip
    Git Fetches the pinned application components
    Python 3.12 with pip and venv Runs application validation, composition and post-provision configuration
    Docker (optional) Builds images locally. Without Docker, images are built remotely in Azure Container Registry

    Step 1: Get the code

    git clone --branch v4.3.0 https://github.com/Azure/agent-landing-zone.git
cd agent-landing-zone

    This pins the coordinated v4.3.0 release, including UI v3.3.0. See the component pins and versioned upgrade requirements.

    You can also initialize a template with azd init -t Azure/agent-landing-zone. That command uses the template's current default branch unless you supply --branch v4.3.0. Continue from the project directory and use the environment selected during initialization rather than creating it again in Step 2.

    infra/main.parameters.json ships with the repository and is regenerated by the hooks. Set the documented deployment variables with azd env set instead of editing that generated file. See Configuration.

    Prepare Python

    The validation hooks need Python packages before provisioning starts. Create a virtual environment from the repository root:

    python -m venv .venv

    If python is not available on Linux or macOS, use python3 -m venv .venv.

    Activate it with .\.venv\Scripts\Activate.ps1 in PowerShell on Windows, or source .venv/bin/activate in Bash on Linux or macOS. Then install the hook dependencies:

    python -m pip install -r config/requirements.txt

    Keep that environment active when running the commands below.

    Step 2: Sign in and create an environment

    az login
azd auth login
azd env new <environment-name>
azd env set AZURE_LOCATION <region>
azd env set NETWORK_ISOLATION false

    Step 3: Choose a topology

    DEPLOYMENT_TOPOLOGY controls where the orchestrator runs.

    Value Orchestrator Administrative panel Application Cosmos DB
    hosted-no-panel (default for new environments) Foundry hosted agent Not deployed Not deployed
    hosted-panel Foundry hosted agent Deployed Deployed
    classic Container App Not applicable Deployed

    Keep the default for a new hosted deployment. To run the orchestrator agent in Container Apps instead, set azd env set DEPLOYMENT_TOPOLOGY classic. The Foundry Agent Service foundation can also have its own backing resources. The application Cosmos DB column does not describe those resources.

    The legacy flags still work when DEPLOYMENT_TOPOLOGY is not set: DEPLOY_HOSTED_AGENT_ORCHESTRATION=false selects classic, and DEPLOY_HOSTED_AGENT_ORCHESTRATION=true with DEPLOY_ADMINISTRATIVE_PANEL=true selects hosted-panel. An explicit DEPLOYMENT_TOPOLOGY always wins.

    Choose ingestion independently

    Versioned upgrade requirement

    Ingestion-free deployments require the coordinated platform v4.3.0 / UI v3.3.0 combination. On platform v4.2.3 / UI v3.2.2, explicitly set DEPLOY_INGESTION_CONTAINER_APP=true before provisioning: the older UI ignores the selection for attachments. See versioned compatibility requirements.

    Fresh environments default to DEPLOY_INGESTION_CONTAINER_APP=false. The default foundry_iq / azureBlob configuration uses native ingestion for the configured Blob source. It does not need the ingestion Container App. Native ingestion does not provide every capability of Agent App Ingestion. Check your source kind, retrieval backend, source/index bindings and required ingestion features before choosing it.

    To select the optional application before provisioning:

    azd env set DEPLOY_INGESTION_CONTAINER_APP true

    This choice works with both classic and hosted orchestration. It does not switch the retrieval backend, rebind sources or indexes, or change UI authentication. Existing environments keep their prior selection, and explicit custom definitions keep their declared components. See Ingestion application selection.

    With the UI v3.3.0 gate, disabling ingestion disables attachment controls and rejects stale/direct uploads before resolving an ingestion endpoint. Chat, authentication and retrieval remain available. Native source ingestion does not implement conversation uploads. Select the optional app when those uploads are required, subject to the existing eligibility checks.

    Step 4: Deploy

    Classic topology

    azd up

    Hosted topologies (hosted-no-panel, hosted-panel)

    The hosted agent needs an image digest before it can be created, so the first deployment has an extra preparation step:

    azd provision
pwsh scripts/prepareHostedDeployment.ps1
azd provision
azd deploy

    On Linux or macOS, replace the preparation command with ./scripts/prepareHostedDeployment.sh. See Hosted agents for what each step does. azd deploy can reuse an already prepared image. If the pinned orchestrator source or startup command changes, prepare a new image and run the second provision again before deploying.

    If the second provision step reports insufficient quota for an unchanged deployment that already exists in the same account, see Quota check rejects an unchanged existing deployment. Do not bypass the quota gate to complete this sequence.

    What happens during the deployment

    Stage Hook What happens
    Application validation (azd up) preup Validates the selected definition and checks its environment binding before the deployment pipeline creates resources.
    Preflight preprovision Checks that the region offers the required services and that quota is available.
    Provision Bicep deployment Deploys the infrastructure from infra/, including placeholder Container Apps for the selected components.
    Post-provision postprovision Configures Foundry, Azure AI Search, Container Apps and role assignments, and publishes runtime settings to App Configuration with the label agent-lz.
    Deploy predeploy Validates the environment, clones each selected component at the commit pinned in manifest.json, builds its image and deploys it.

    Verify

    1. Run azd env get-value AZURE_RESOURCE_GROUP and open the resource group in the Azure portal.
    2. Open the Container App whose name ends with frontend and browse to its URL.
    3. Upload a document to the configured source (documents for the default Blob configuration). Verify that the configured ingestion path has processed it. Do not expect an ingestion Container App or chat attachment controls in a fresh native deployment.
    4. Ask a question about the document in the UI, then verify document allow/deny behavior with the intended user identities. A successful answer alone does not prove authorization.

    Clean up

    azd down --purge

    Review the listed resources before confirming. This deletes the deployed resources and their data, including purged resources that cannot be recovered. Reused resources outside the deleted resource groups can remain.
