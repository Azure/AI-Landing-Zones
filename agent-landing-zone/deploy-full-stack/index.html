    Full stack deploy

    Deploy the Azure foundation and the bundled agent application: a web UI, an orchestrator and, when selected, an ingestion application. Choose where the orchestrator runs and how the deployment connects to Azure before provisioning.

    Only need the foundation? Use Deploy infrastructure only. For the relationship between the template, its manifest and lifecycle hooks, see How the template works.

    Prerequisites

    • Permissions: Owner, or Contributor plus User Access Administrator, at the required deployment scopes. Shared networks, DNS and monitoring can require additional permissions in their own scopes. See Permissions.
    • Subscription readiness: accepted Responsible AI terms, registered resource providers, supported service/model regions and sufficient quota for the selected parameters. Regional considerations explain why passing preflight does not guarantee available capacity.
    • Private deployments: an authorized VPN/VNet-connected deployment host with private DNS resolution. An ACR Tasks build pool is not that host.
    Tool Required for
    Azure Developer CLI (azd) and Azure CLI (az) Provisioning and lifecycle hooks; use current supported versions
    PowerShell 7 Windows hooks and cross-platform preflight checks
    Bash, jq and curl on Linux/macOS POSIX hooks and dependency bootstrap
    Git Fetching selected, pinned application sources
    Python 3.12 with pip and venv Validation, composition and service configuration
    Docker, when using local builds Optional for supported Container App builds; hosted preparation uses ACR Tasks
    Foundry agents azd extension (azure.ai.agents) Hosted deployment; install with azd extension install azure.ai.agents if absent

    Cost and time

    Provisioning creates billable resources before the application is ready. Review the foundation inventory and cost scenarios and cost guide, then budget for application runtime, model usage and data. First deployments take longer because of resource creation, image builds, role propagation and private-link approvals. There is no fixed completion time.

    Step 1: Get the code

    git clone https://github.com/Azure/agent-landing-zone.git
cd agent-landing-zone

    The repository's default main branch is the stable deployment source, not develop. Record the resolved commit for repeatable deployments. To deliberately select a published release instead, use git fetch --tags and git checkout <release-tag> before continuing.

    Alternatively, azd init -t Azure/agent-landing-zone initializes the current default template in an empty directory. Reuse the environment it creates rather than creating it again in Step 2.

    Prepare Python

    From the repository root:

    python -m venv .venv

    On Linux/macOS, use python3 if python is unavailable. Activate .\.venv\Scripts\Activate.ps1 in PowerShell or source .venv/bin/activate in Bash, then install:

    python -m pip install -r config/requirements.txt

    Keep this environment active for the lifecycle commands.

    Working from your own repository

    An unmodified deployment needs only the platform checkout. Hooks fetch selected runtime components automatically; four forks are not required. Fork or mirror the platform when you maintain deployment inputs or automation, and fork only the runtime components whose source you change.

    Keep reviewed, nonsecret inputs in source control and apply them explicitly with azd env set; an environments/ folder is not loaded automatically. Protect .azure/, credentials, sibling component workspaces and deployment logs. For private components, configure Git read access on the actual deployment host separately from Azure authentication. Never embed tokens in repository URLs. See Custom applications for source pinning and composition.

    Step 2: Select the deployment target

    The following creates a new environment. Replace all placeholders:

    az login
azd auth login
az account set --subscription <subscription-id>
azd env new <environment-name>
azd env set AZURE_SUBSCRIPTION_ID <subscription-id>
azd env set AZURE_RESOURCE_GROUP <dedicated-resource-group>
azd env set AZURE_LOCATION <region>

    For an existing environment, use azd env select <environment-name> instead and preserve its approved inputs. Use separate environments, resource groups, identities, secrets and data for DEV, TEST and PROD. An environment name or the App Configuration label alone is not a security boundary. Promote the same reviewed source revision with stage-specific inputs.

    Step 3: Choose the application and network

    Orchestrator topology

    DEPLOYMENT_TOPOLOGY chooses where the agent orchestrator runs. It is independent of the foundation's standalone or hub-and-spoke network shape.

    Value Orchestrator runs in Administrative panel Application Cosmos DB
    hosted-no-panel Foundry Agent Service Not deployed Not deployed
    hosted-panel Foundry Agent Service Deployed Deployed
    classic Azure Container Apps Not applicable Deployed

    A new environment defaults to hosted-no-panel. To choose another value before first provision, for example Container Apps:

    azd env set DEPLOYMENT_TOPOLOGY classic

    Existing environments retain their recorded topology. Older environments without a topology marker resolve to classic; do not change them merely to match a new-install default. The table describes application resources, not the Foundry Agent Service's separate backing resources. See Hosted agents for identity, continuity and panel semantics.

    Ingestion and custom applications

    Fresh environments default to DEPLOY_INGESTION_CONTAINER_APP=false, using native Foundry IQ ingestion for the configured default Blob source. Select the optional app before provisioning if its ingestion features or eligible conversation uploads are required:

    azd env set DEPLOY_INGESTION_CONTAINER_APP true

    This does not switch the retrieval backend or rewrite source/index bindings. Existing environments keep their selection. Before disabling an existing app, review ingestion choices and the older-UI migration warning. Disabling uploads must not be inferred from a missing endpoint.

    For a different application, set AGENTLZ_APP_DEFINITION to its definition path before the first provision. The environment binds to that application ID. Use Custom applications for its contract and component-specific deployment requirements; do not substitute bundled hosted preparation for a custom definition's build flow.

    Network and build mode

    Choose one network posture for this new environment:

    Choice Inputs and preparation
    Public service endpoints azd env set NETWORK_ISOLATION false; authentication and authorization still apply
    Private, self-contained network azd env set NETWORK_ISOLATION true; review the standalone design
    Private spoke using an existing hub NETWORK_ISOLATION=true, explicit hub routing, peering, DNS and shared-service inputs from the hub-and-spoke reference
    Existing VNet Review subnet ownership, delegations, NSGs and BYO parameters before enabling USE_EXISTING_VNET

    Apply the approved foundation inputs from infrastructure choices. Do not change NETWORK_ISOLATION on an existing environment as a retry shortcut. With isolation enabled, run configuration, preparation and deployment from the connected host. If creating that host first, use the deferred post-provision procedure.

    Image build path Selection
    Public registry, remote builds azd env set BUILD_MODE acr-task; supported components use regular ACR Tasks
    Private registry, remote builds Keep DEPLOY_ACR_TASK_AGENT_POOL=true before provision and use BUILD_MODE=acr-task; builds use the provisioned VNet pool
    Supported Container Apps, local Docker azd env set BUILD_MODE local; the host must reach the registry and service endpoints

    Automatic hosted image preparation and isolated custom source builds still require the private pool. BUILD_MODE=local is not a local-build alternative for those paths. See network isolation for build egress, DNS and private-link readiness requirements.

    Step 4: Deploy

    Confirm the target before creating or changing resources:

    azd env get-value AZURE_SUBSCRIPTION_ID
azd env get-value AZURE_RESOURCE_GROUP
azd hooks run preup

    Resolve validation, quota, Policy and connectivity failures rather than bypassing checks. The explicit preup check also validates binding before standalone provisioning, which otherwise runs its check after azd may initialize a resource group.

    Container Apps orchestrator (classic)

    azd up

    This runs provisioning, post-provision service configuration, image builds and application deployment.

    Foundry orchestrator (hosted-no-panel or hosted-panel)

    Confirm the runner has Foundry agent authoring access on the exact project (Foundry User, previously Azure AI User, or an appropriate equivalent), account read access and the required scoped role-assignment authority. Azure sign-in or network connectivity alone is insufficient; see private-runner permissions and hosted identities.

    A fresh bundled hosted deployment needs this order:

    azd provision
pwsh scripts/prepareHostedDeployment.ps1
azd provision
azd deploy

    On Linux/macOS replace the preparation command with ./scripts/prepareHostedDeployment.sh.

    Stage Result
    First provision Creates the foundation and configures its services
    Preparation Fetches the pinned orchestrator source, builds its hosted image and records an immutable digest
    Second provision Materializes the image and Foundry deployment handoff
    Deploy Creates the hosted version, bootstraps runtime access, smoke-tests it and deploys the other selected apps

    A fresh azd up does not build the missing hosted handoff. If you started with it, complete preparation, the second provision and deployment. If the first provision deferred configuration, complete that work before preparation. Do not skip the second provision or replace the digest with an image tag. If the second provision rejects quota for an unchanged deployment, inspect quota diagnostics rather than bypassing the gate.

    For an already configured infrastructure-only environment, reuse the same checkout, inputs and bound application. In classic, continue with azd deploy. In a bundled hosted topology, continue at preparation above.

    Verify

    1. Inspect the selected resource group and intended deployed revisions, not just an older healthy placeholder:

      azd env get-value AZURE_RESOURCE_GROUP
az containerapp list -g <resource-group> \
  --query "[].{name:name,state:properties.runningStatus,revision:properties.latestReadyRevisionName}" -o table

    2. Open the frontend URL from the deployment outputs or its Container App ingress configuration. Private endpoints require a connected browser. Complete Entra sign-in and delegated-authentication configuration for the intended users.

    3. Exercise an agent task and its configured tools with representative identities. If using documents, add a test document to the configured source, confirm its ingestion, and test both allowed and denied document access. Test uploads only when the ingestion app and upload eligibility are selected.
    4. In a hosted topology, verify the intended routed version and runtime telemetry as well as the remaining Container Apps. A greeting smoke test is not evidence of user login, OBO or document authorization.

    Use Troubleshooting for failures. Do not authorize a cutover based only on a successful hook or HTTP 200.

    To make a hosted agent available in Teams and Microsoft 365 Copilot, continue with Publish to Teams and M365. Bot creation and channel publication are separate manual tasks, not part of this deployment.

    Lifecycle

    Run these tasks from the platform root with the intended environment selected, Python active, both CLIs authenticated and private connectivity available when required. Record the source revision, manifest, definition, approved inputs and hosted digest before a change. Back up configuration and relevant data using service-specific procedures.

    Upgrade to a new release

    1. Read the target release notes, component versions and migrations. Upgrade the compatible platform combination, including its repository-owned infra/, rather than independent component tips.
    2. Fetch and check out the approved release tag. Reconcile local platform/runtime changes and update bundled manifest/definition pins together.
    3. Preserve the existing topology, ingestion selection, resource naming and source/index bindings. Follow ingestion migration guidance before opting out or downgrading an older UI.
    4. Run the matching deployment workflow. For a generated hosted image with a changed source pin, prepare it again and provision its handoff before deployment. Validate in DEV before promoting the same revision.
    5. Repeat the application checks, including authorization and any ingestion, history or continuity features in use.

    GPT-RAG v3 environments

    A v3 environment cannot be upgraded in place to Agent Landing Zone v4. Deploy a new environment, migrate the required documents, indexes and conversation data, and validate it before retiring the old environment.

    Redeploy applications only

    When foundation outputs, application binding, component selection and the image handoff remain compatible:

    azd deploy

    Bundled Container Apps use the manifest's verified sibling checkouts. Preserve local work and relocate a stale checkout so the hook can fetch the selected revision; it does not advance an existing checkout automatically. Child logs are under each component's .logs directory and can contain sensitive details.

    Hosted deployment reuses the prepared digest. A changed generated source pin or image requires preparation, provisioning the handoff and deployment again. An operator-managed digest is not rebuilt automatically: verify its provenance, compatibility and registry availability. Rebuilding identical source separately in each environment does not prove identical image digests.

    Infrastructure, RBAC, topology or ingestion-selection changes require the full workflow, not deploy-only. Changing a selection does not delete previously deployed resources or revoke old permissions; retirement is separately authorized.

    Change a runtime setting

    First check configuration ownership and overwrite behavior. Provisioning-managed inputs must be changed in their source and applied through the full workflow. For a directly managed, nonsecret runtime key:

    az appconfig kv set --endpoint <app-config-endpoint> --auth-mode login \
  --key <KEY> --value <value> --label agent-lz --yes

    Restart each affected Container App revision to reload it:

    az containerapp revision restart -g <resource-group> -n <container-app-name> \
  --revision <revision-name>

    For a hosted version, run root azd deploy with the compatible handoff. Process environment inputs declared in hosted-agent/azure.yaml are immutable version inputs and require a new agent version. An App Configuration edit cannot replace a process-only setting such as APP_CONFIG_TLS_COMPATIBILITY. The agent-lz label is not an environment-isolation mechanism.

    Rotate a secret

    Inspect the Key Vault reference before rotating. An unversioned URI resolves the current secret version when configuration reloads; a versioned URI must be updated deliberately. Add the new secret version through your approved secure process, preserve required access, then restart affected Container App revisions or redeploy the hosted version. Verify the new credential before retiring the old one. Never place secrets in plaintext App Configuration or command logs.

    Recover hosted runtime access

    The bundled post-deploy hook normally bootstraps the discovered runtime principal. To review the exact read-only role plan from the root's selected environment:

    python -m config.deployment.hosted_access --azd-env --plan

    An authorized administrator can reconcile only that plan with the idempotent wrapper:

    pwsh scripts/bootstrapHostedAccess.ps1

    On Linux/macOS use ./scripts/bootstrapHostedAccess.sh. The wrapper selects hosted-agent / orchestrator-agent by default; custom services use their own project/service context. Allow role propagation, then retry root azd deploy so the greeting and remaining deployment gates run before cutover.

    The closed bootstrap set grants App Configuration Data Reader, model access and, when configured, access to the exact audit secret. It is not a grant to delegated users or a replacement for all capability profiles. Do not grant Owner or remove unrelated assignments to recover. See hosted identities.

    Roll back to a previous release

    Review migration constraints and restore the previous complete compatible combination and its inputs. When only classic application pins changed and the foundation remains compatible:

    git checkout <previous-release-tag>
azd deploy

    If infrastructure or configuration changed, review and rerun the full workflow. Hosted rollback requires the previous pinned image to be prepared, or its verified digest deliberately restored, then provisioned and deployed. Checking out an old tag does not reverse data migrations. Restore ingestion requirements before downgrading to a UI without the upload gate. Some changes require forward repair or a new environment with data migration. azd down --purge is not rollback.

    Remove an environment

    Destructive action

    Confirm the subscription, resource group and deletion prompt. Export or back up required documents, indexes, configuration and conversation data. Check retention obligations and shared-resource dependencies first.

    azd env select <environment-name>
azd env get-value AZURE_SUBSCRIPTION_ID
azd env get-value AZURE_RESOURCE_GROUP
azd down

    Use --purge only when permanent removal of supported soft-deleted resources is explicitly intended. It removes recovery options. Reused resources outside the deletion scope and manually created links can remain and continue incurring charges. For a spoke, retire only its own hub peering/DNS links with their owners; do not delete shared hub, DNS or monitoring resources.
