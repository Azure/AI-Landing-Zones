    Troubleshooting

    This page lists the errors you are most likely to see, grouped by the deployment stage that raises them. Each entry shows the message, the cause, and the fix.

    Every stage writes its output to the terminal. Component deployments also write logs to the .logs folder of each component checkout.

    Sharing diagnostics

    When you ask for help, share the failing command, the error message, and the specific non-secret settings involved (for example NETWORK_ISOLATION, BUILD_MODE, AZURE_LOCATION). Do not paste the full output of azd env get-values. It can contain sensitive values, endpoints and identifiers. Remove tokens, cookies, credentials, signed URLs and private environment names from diagnostics.

    Deploy stage

    The root predeploy hook checks the provisioned foundation and application binding before deploying applications. It then resolves the selected topology, checks private reachability and pool requirements, and validates the hosted handoff when applicable. The entries below group failures by cause, not execution order.

    Hosted deployment is not prepared

    Symptom. Deploying a hosted topology stops and asks you to run the preparation script.

    Cause. Hosted deployment needs provisioned prerequisites, an immutable image digest and a provisioned deploy handoff. The first provision sets HOSTED_AGENT_PREPARED=true. The preparation script records the digest, but only a subsequent provision materializes DEPLOY_HOSTED_AGENT=true. It does not create the data-plane agent version.

    Fix. First provision the foundation and complete post-provision configuration if that has not already happened. Then run:

    pwsh scripts/prepareHostedDeployment.ps1
azd provision
azd deploy

    Use ./scripts/prepareHostedDeployment.sh on a shell host. A first azd up can stop at this handoff without completing deployment. Do not set the output flags manually to bypass it. For an already-prepared same-image retry, see Hosted redeployment.

    Hosted agent deployment returns an agent permission denial

    Symptom. Agent creation or lookup returns HTTP 403 and names Microsoft.CognitiveServices/accounts/AIServices/agents/read as a missing action.

    Cause. The actual deployment principal lacks Foundry agent data-plane permissions. Successful private DNS/TLS checks and ARM provisioning do not prove agent authorization.

    Fix. Verify the object ID in the denial against the identity used by azd auth login. An authorized administrator can grant Foundry User (formerly Azure AI User) at the target Foundry project scope for a runner that creates and updates agents. Verify the assignment, allow propagation, then retry. Do not substitute Azure AI Developer, which targets workspace/hub scenarios, or grant resource-group Owner. See Connected-host deployment. This authoring role is not delegated-user/OBO acceptance evidence.

    Application definition does not match the environment

    Symptom. predeploy exits with code 2 after validating the application definition.

    Cause. The selected definition's application ID differs from AGENTLZ_APP_ID in the environment binding. An invalid definition instead fails validation with exit code 1. A custom azure.ai.agent component does not, by itself, require changing the bundled orchestrator from classic to hosted topology.

    Fix. Restore the matching definition. Use a separate environment for a different application ID rather than deleting the binding to bypass the check. A custom definition must be selected before the first provision, not merely before the first deploy. Changing the bundled topology is not a generic fix for an application-ID mismatch. See Custom applications.

    Custom hosted image pull fails with a classic bundled orchestrator

    Symptom. A custom azure.ai.agent service cannot activate its private image, even though the selected environment has Foundry project and registry outputs.

    Cause. Before the correction tracked in agent-landing-zone#779, a custom hosted definition with a classic bundled orchestrator could leave prepareHostedAgent=false. This omits the existing declarative AcrPull assignment for the foundation's Foundry project managed identity. Publishing the endpoint or reconciling per-instance capability profiles does not replace that foundation image-pull preparation.

    Fix. The correction shipped in v4.2.3 and is included in v4.3.0. Composition now selects hosted foundation preparation for a custom hosted component even when the bundled orchestrator remains classic. It does not enable the bundled hosted orchestrator or change classic routing.

    For an environment provisioned before the correction, use the complete shipped platform release, select the same environment, and keep the same application definition and immutable image. From the platform repository root, run azd hooks run preup, azd provision, azd env refresh, then azd deploy. Use a VNet-connected host for private environments. Provisioning applies the project-identity registry pull grant. Refreshing outputs alone cannot apply it. For external registries, verify the configured registry resource and its supported pull-role mode rather than assuming the default registry's assignment covers them.

    Do not grant broad roles manually, enable registry admin credentials, or substitute an OIDC connection or service identity for delegated-user/OBO authentication. Deployment still verifies the routed version and actual instance identity, reconciles the exact declared capability profiles, and only then runs the protocol greeting smoke. This is not evidence that all runtime identity grants precede image pull, or that recovery, first deployment, OBO, citations, or document allow/deny acceptance has passed. See Source pinning.

    Private deployment prerequisites failed

    Message.

    Private deployment prerequisites failed. Use a VPN/VNet-connected host; RUN_FROM_JUMPBOX is not a connectivity bypass.

    Cause. NETWORK_ISOLATION=true and the host cannot resolve or open a TLS connection to App Configuration, or to the Foundry project endpoint for hosted topologies. The check waits up to 20 seconds per endpoint.

    Fix. Run the deployment from the jumpbox or from a host connected through VPN or a peered VNet. Setting RUN_FROM_JUMPBOX does not skip this check. See Verify private connectivity.

    ACR Task agent pool is missing

    Message.

    Run 'azd env set DEPLOY_ACR_TASK_AGENT_POOL true' and 'azd provision', or set BUILD_MODE=local on a VNet-connected host with Docker.

    Cause. NETWORK_ISOLATION=true, the selected environment has no ACR_TASK_AGENT_POOL output, and BUILD_MODE is not local. The root hook stops before applications are touched. This guard also applies when a custom service supplies a prebuilt digest.

    Fix (recommended). Provision the agent pool:

    azd env set DEPLOY_ACR_TASK_AGENT_POOL true
azd provision
azd deploy

    Fix (alternative for supported Container App builds). Build on a VNet-connected host that has Docker installed:

    azd env set BUILD_MODE local
azd deploy

    The jumpbox does not include Docker by default. BUILD_MODE=local does not provide a local fallback for automatic hosted image preparation or isolated custom source builds. Those paths still require the pool unless you deliberately supply a compatible, already-built immutable image. See Image builds in isolated deployments.

    Package installation fails inside the build pool

    Symptom. An ACR run starts in the private agent pool, but package installation fails. For example, npm reports Exit handler never called!, followed by tsc: not found during the frontend build.

    Diagnosis. Retrieve the actual failed ACR run log from a VNet-connected host. Correlate its timestamps and the build-agent source address with Azure Firewall deny logs. An existing pool and a successfully pulled base image do not prove that package feeds are reachable. Check the exact pinned lockfile's resolved URLs. Setting npm's registry alone does not replace those URLs.

    Fix. The pinned orchestrator's four Microsoft npm feeds and *.vsblob.vsassets.io redirect CDN are included in the Agent Landing Zone default build allowlist. Confirm that the ACR Task agent pool and extendFirewallForAcrTaskBuilds are enabled and that the updated firewall configuration has been provisioned. packages.microsoft.com is already allowed by the OS-package rule. Do not add it as a missing host. For other dependencies, if firewall logs confirm blocked package hosts, add only the required feeds and their verified download CDN to parameters.additionalAcrTaskBuildFqdns.value in main.parameters.json, provision, and retry the same pinned source. See Application-specific package feeds. Keep the exception confined to build-subnet HTTPS traffic. Do not upgrade npm speculatively or treat a later missing compiler as proof of a dependency version defect.

    Stale component checkout

    Message contains Remove or relocate the stale sibling checkout.

    Cause. predeploy uses sibling checkouts for bundled Container App components. A folder with the component's name already exists at a different commit from the manifest pin. Do not assume that matching HEAD also proves that the checkout has no local modifications.

    Fix. Inspect and preserve any local work, then move the folder named in the message and run azd deploy again to obtain the pinned checkout. Delete it only if you have confirmed it contains nothing you need. Keep component development in a separate folder.

    A component deployment fails

    Cause. The build or the container app update for one component failed.

    Fix. Open the newest file in the .logs folder of that component checkout. Common causes are a registry that the build host cannot reach (see the agent pool entry above) or a missing role assignment for your identity on the registry.

    Deploy succeeds but the UI or administrative panel does not start

    Symptom. Child deployment commands return success, but the latest application revision is unhealthy. The UI reports missing OAUTH_AZURE_AD_CLIENT_ID, OAUTH_AZURE_AD_CLIENT_SECRET, or OAUTH_AZURE_AD_TENANT_ID. A selected ingestion app reports missing OAuth panel settings.

    Cause. Hosted UI startup validates the default user-delegated OAuth contract. The panel also requires Entra configuration. A previous healthy placeholder revision can still serve HTTP 200 while the new image fails.

    Fix. Check the latest revision's image, health, and startup logs. Configure the delegated authentication settings, store the client credential in Key Vault, and publish only its reference with label agent-lz. Restart the intended revision and verify its health, the Entra login redirect, and rejection of unauthenticated panel data requests. Then verify real user login, OBO, and document authorization. Do not switch to service identity or disable the panel to turn a missing-authentication failure into a passing acceptance result.

    Provision and post-provision stages

    Search shared private links are not ready

    Symptom. Private native azureBlob source configuration stops with administrator approval instructions, denied Search reads or a readiness timeout.

    Cause. Search-managed outbound access is not ready for the exact required target/group. A pending connection, a successful ARM deployment or a private endpoint reachable by the runner does not prove Search's outbound link is ready.

    Fix. Use the reported Search resource, link name, target and group to investigate the exact deployment request. A pending link fails immediately: ask an authorized administrator to verify and approve only that request, following Microsoft's procedure, sections 2 and 3, then rerun post-provision from a connected host. If polling times out, check the exact link state and allow propagation before retrying. Already-approved connections proceed only when the exact source link reports both Approved and Succeeded, without target PEC access. An approved link still provisioning uses a 600-second readiness budget, 10-second polling and requests limited to at most 30 seconds by the remaining budget. The gate runs before dependent Search mutation and before native source creation. Do not approve unrelated requests, grant broad Owner access, enable public network access or bypass the gate. See Private native Blob ingestion.

    An ARM 401/403 stops configuration immediately. The existing runner identity needs Microsoft.Search/searchServices/sharedPrivateLinkResources/read. Administrator approval does not replace that Search read permission. Rejected/disconnected or failed links are not automatically overridden. The backend endpoint can belong to a Microsoft-managed tenant, so its target PEC ID need not be a Search or shared-link ID. Configuration does not auto-approve by request-message text, a name substring or an assumed <shared-link-name>.<GUID> convention. It does not enumerate target PECs.

    The template publishes SEARCH_SHARED_PRIVATE_LINKS under label agent-lz. Older short-name deployments can use the prior deterministic naming rules. If a bounded long name has no manifest, configuration refuses to guess its hash: re-provision with the updated template in a separately authorized deployment, then retry configuration. Paginated or unreadable target collections do not prevent readiness once the exact source Search links are Approved and Succeeded. Do not edit the manifest to authorize an unrelated request.

    Ingestion selection does not match the source configuration

    Symptom. No ingestion Container App appears in a fresh environment, or configuration rejects an unsupported ingestion combination.

    Cause. DEPLOY_INGESTION_CONTAINER_APP=false is the fresh bundled application default, independently of classic/hosted orchestration. Native ingestion requires a supported, configured Foundry IQ source. It does not cover all Agent App Ingestion features. Existing environments and explicit custom definitions retain their component intent.

    Fix. Check the resolved component selection, retrieval backend, source kind and source/index bindings. If application-managed ingestion is required, explicitly select the app and rerun the full provisioning/deployment workflow. Opt-out also supports an explicitly named SEARCH_RAG_INDEX_NAME populated by an independent pipeline for ai_search, or for foundry_iq with pattern and kind searchIndex. Those modes do not acquire native ingestion merely because the application is omitted. Unsupported source combinations and enabled conversation uploads fail validation when the app is omitted. Do not silently remove an existing app or change UI authentication to repair selection. See Change ingestion selection safely.

    Check the version before repairing uploads. Ingestion-free operation requires the platform v4.3.0 / UI v3.3.0 manifest-pinned combination. Follow the versioned migration.

    On platform v4.2.3 / UI v3.2.2, attachments still depend on the ingestion application's upload endpoint. Retain or restore DEPLOY_INGESTION_CONTAINER_APP=true and use the complete workflow. Clearing INGESTION_BASE_URL or DATA_INGEST_APP_ENDPOINT is not an opt-out, and a native Search source endpoint is not an upload endpoint. Manually setting [features.spontaneous_file_upload].enabled=false is not a supported workaround for UI v3.2.2: authenticated startup overwrites it, and Entra Copilot settings independently force uploads on. Preserve the authentication policy. Do not select anonymous mode to hide attachments.

    In the UI v3.3.0 contract, a missing App Configuration key keeps legacy behavior. Explicit false hides controls and rejects server uploads and client preflight before endpoint/Dapr resolution. true retains existing eligibility checks. If attachments remain available after opting out, verify the deployed manifest-pinned UI revision and the effective key under label agent-lz, rather than changing authentication or clearing endpoints. Normal text chat, authentication and retrieval remain available. Native source ingestion does not implement conversation uploads.

    Shared-source permission options are rejected or unexpected

    Cause. Omitted or actual-null FOUNDRY_IQ_INGESTION_PERMISSION_OPTIONS retains ["rbacScope"]. Explicit [] is not an omitted value. For active native Blob ingestion it selects a deliberately shared source only with foundry_iq, the azureBlob pattern (or historical managed compatibility alias), azureBlob source kind and recognized non-ADLS configuration. Active ADLS, source mismatches and ambiguous ADLS configuration fail closed. For inactive native Blob ingestion, infrastructure-published [] remains accepted as unused metadata for ai_search (any pattern) and foundry_iq / searchIndex. No native Blob source is rendered in these modes. This is not a shared-source opt-in. Nonempty non-ADLS Blob lists accept only rbacScope and sensitivityLabels. Malformed JSON, scalars, textual null, non-string/blank entries and unsupported names fail closed with actionable diagnostics.

    Fix. Supply valid JSON matching the intended source policy. Do not use [] as an authentication, RBAC or private-link workaround. Restore ["rbacScope"] for protected ingestion and rerun source configuration, then verify the resulting permission metadata and document allow/deny behavior. Other sources and Entra ID/OBO remain protected by their existing contracts. See Explicit shared-source permission options.

    Firewall DNS proxy is enabled but clients still resolve incorrectly

    Cause. ENABLE_FIREWALL_DNS_PROXY=false is the default. The opt-in applies only when firewall deployment and network isolation are enabled. It does not modify VNet or VPN DNS settings or affect build-feed egress. Proxy enablement does not prove that clients use the firewall or that private DNS zone links and forwarding are correct.

    Fix. Check the actual client DNS server, the intended forwarding path and private-zone links. Keep client DNS changes deliberate and separate from the proxy selection. Do not redirect clients automatically or enable public access as a workaround. See Opt-in firewall DNS proxy.

    Hosted configuration TLS handshake stalls

    Symptom. The hosted container cannot finish loading App Configuration or resolving its Key Vault references despite verified private connectivity. The compatibility correction below requires Agent Landing Zone v4.2.3 or later with agent-app-orchestrator v5.2.1 and its hosted deployment definition.

    Diagnosis. Distinguish DNS/routing/firewall failures, TLS handshake stalls, and HTTP authentication/authorization responses. Verify both endpoints from the relevant network, the actual runtime identity and its existing minimum roles. Do not treat a TLS success as proof of document authorization or infer that MTU is the established cause of every timeout.

    Fix. For a confirmed transport compatibility case, use the endpoint-scoped, verified configuration TLS profile. Supply the actual application KEY_VAULT_URI, set APP_CONFIG_TLS_COMPATIBILITY=true and deploy the corrected agent version. Disable the profile with false and redeploy to restore the SDK default. Never use verify=False, downgrade globally to TLS 1.2, change caller identity or broaden RBAC to disguise the failure.

    If bootstrap unexpectedly tries to resolve a UI-only Key Vault reference, check the orchestrator's null-label selector: SDK None selects every label, whereas "\0" selects only unlabelled settings. Use the corrected selector without removing existing service-specific labels or weakening vault access. The correction is already included in the v4.3.0 pinned combination. It does not imply agent-lz-only reads across components. See actual selectors and overwrite behavior.

    Search preflight region and quota

    Symptom. Foundation preflight reports Search provider availability or quota for AZURE_LOCATION even though AZURE_SEARCH_LOCATION selects another region, or accepts quota for only one service when two Search services will be created.

    Cause. Older preflight code could check the primary region instead of the effective searchServiceLocation, or miss the Foundry Search creation path. Both were corrected in v4.2.3 and are included in v4.3.0. Checking only the primary region or only the application Search service does not match a deployment that creates both.

    Fix. Verify AZURE_SEARCH_LOCATION. An unset or empty value uses AZURE_LOCATION. Both the general and Foundry Agent Service Search services use this region, and both provider availability and Search quota checks must use it. Quota must cover one service for deploySearchService, plus one for Foundry when deployAiFoundry and deployAAfAgentSvc are enabled and no aiSearchResourceId is supplied. If both paths create a service, quota for only one is insufficient. Choose a supported region with capacity or request a quota increase. If the installed platform still checks the wrong region or count, verify that the local hooks and repository-owned infrastructure match the shipped release. Do not treat an older preflight result as passed. Do not set PREFLIGHT_SKIP or AGENTLZ_REGIONAL_PREFLIGHT_SKIP to bypass it. See Search region and quota.

    Quota check rejects an unchanged existing deployment

    Symptom. Re-provisioning an existing environment reports less remaining model quota than the configured capacity, although that same account already has the requested deployment at that capacity.

    Cause. In v4.2.2, both preflight gates compare the full requested capacity with unused regional quota. They do not credit capacity already allocated to the target deployment, so the second provision step of a hosted deployment can stop before Azure receives the incremental update.

    Fix. Verify the selected environment, account location, deployment name, model/version and SKU. Do not disable preflight, reduce capacity just to pass the check, or delete the existing deployment. Agent Landing Zone v4.2.3 includes the correction tracked in agent-landing-zone#773. The shipped code uses one shared quota calculation for both gates. It credits only a verified, successful matching deployment in the selected subscription and resource group, checks increases against the remaining quota, and aggregates deployments using the same quota pool. Fresh allocations and unverified or changed targets still need their full capacity. Model availability checks remain in place. For older releases, record this as a preflight limitation, not successful hosted deployment acceptance.

    Foundry rejects evaluation API-key creation

    Message. Failed to list key. disableLocalAuth is set to be true.

    Cause. The Foundry account requires Microsoft Entra ID. In v4.2.2, post-provision still attempts to copy an evaluation API key to Key Vault. Its final success message does not prove that this secret was created. This does not require enabling key authentication for the application.

    Fix. Keep local authentication disabled and use Microsoft Entra ID for evaluation clients. Agent Landing Zone v4.2.3 includes the correction tracked in agent-landing-zone#773. The shipped code checks the account's authentication setting, explicitly reports key injection as not applicable for Entra-only accounts, and fails on unexpected key or Key Vault errors. For older releases, record this post-provision limitation separately from application runtime results.

    Administrative panel cannot resolve its Cosmos database

    Message. DEPLOY_ADMINISTRATIVE_PANEL is true but DATABASE_ACCOUNT_NAME is not set.

    Cause. In v4.2.2, post-provision publishes the resolved account and database under DATABASE_ACCOUNT_NAME and DATABASE_NAME in App Configuration, but panel role assignment expects them in the process environment.

    Fix. Confirm these two non-secret settings under label agent-lz in the selected environment's App Configuration. For a split recovery, supply those same values to config.panel.setup. Do not infer the database name from a resource-name pattern or widen the grants to the account scope. Agent Landing Zone v4.2.3 includes the correction in agent-landing-zone#773. The shipped code reads the published settings when process inputs are absent and preserves the existing container-scoped roles.

    Missing endpoint output

    Message.

    Missing <KEY>. Run provisioning and load the selected azd environment outputs before this stage.

    Cause. The stage needs an output that the selected azd environment does not have: APP_CONFIG_ENDPOINT, AZURE_AI_PROJECT_ENDPOINT, or AZURE_CONTAINER_REGISTRY_ENDPOINT.

    Fix. Confirm the environment with azd env select <name>, then run azd provision. If you moved to another machine, run azd env refresh to load the outputs.

    Private post-provision prerequisites failed

    Message.

    Private post-provision prerequisites failed. Connect through VPN/VNet and rerun postProvision; configuration has not started.

    Cause. Provisioning completed, but the host cannot reach App Configuration on the private network. No configuration was applied.

    Fix. Connect through the jumpbox, VPN, or a peered VNet, then run:

    azd hooks run postprovision

    Post-provision was deferred

    Message.

    Post-provision configuration explicitly deferred; application setup is incomplete.

    Cause. With isolation enabled, an explicit deferral skips configuration and exits the hook successfully. RUN_FROM_JUMPBOX is false (or 0, no, skip), or AZURE_SKIP_NETWORK_ISOLATION_WARNING is truthy while RUN_FROM_JUMPBOX is not truthy. A truthy RUN_FROM_JUMPBOX requests the connectivity check instead. This warning does not prove that setup ran.

    Fix. Finish the configuration from a connected host. See Post-provision can be deferred and Complete a deferred post-provision.

    NETWORK_ISOLATION is not a boolean

    Cause. The value is something other than true or false.

    Fix.

    azd env set NETWORK_ISOLATION true   # or false

    Provisioning fails in Azure

    Cause. Common causes are model quota in the selected region, a resource name that is already taken, or a policy that denies a resource configuration.

    Fix. Read the failed operation in the Azure portal under Resource group > Deployments. For quota, choose another region or request more capacity. Then run azd provision again. Provisioning is incremental, but a completed ARM deployment does not prove that post-provision or application deployment succeeded.

    Runtime

    The orchestrator returns HTTP 422

    Cause. The stateless Responses 2.0.0 adapter rejects a non-null previous_response_id. It can also return 422 for invalid input, such as an empty ask or a message array that does not end with a user message. Top-level conversation is ignored by the pinned adapter, not a reason for that rejection.

    Fix. Read the returned validation detail, remove state selectors, and send valid, complete, ordered context in each request. The pinned UI uses /invocations?api-version=v1, which has its own request shape. Do not interchange the two request bodies. See Calling the agent.

    Hosted chat works but history is unavailable

    Cause. The hosted runtime is stateless, and the UI does not register the classic orchestrator/Dapr history data layer for CHAT_BACKEND=hosted_agent. Without separately activated continuity, multi-turn context is confined to the active UI session. A reload, new chat or browser restart is not a durable-history test. Application Cosmos DB in hosted-panel stores owner and feedback metadata, not transcripts.

    Fix. Check the intended continuity and panel gates, owner binding and agent-scoped permissions. Disabled panel history surfaces return 503. Continuity requires successful configuration and activation, and invalid owner-binding configuration can prevent UI startup. Rerun the matching provision/deploy workflow after deliberate configuration changes, and verify same-owner access and cross-user denial. Do not register the classic history layer, grant broad conversation access to the hosted container, or infer history acceptance from a greeting. Foundry Agent Service's separate backing resources do not by themselves enable UI history. See Calling the agent.

    The application starts but does not answer

    Check, in this order:

    1. The intended Container App revision and image are healthy, or the routed Foundry agent version is ready. An older placeholder's HTTP 200 is not enough. See Check application health.
    2. The logs show the startup sequence and no configuration errors. See Stream logs from a container app.
    3. Shared runtime settings are published under label agent-lz, but effective values depend on the actual component selectors and overwrite behavior. After changing a setting, restart the affected Container App revision or redeploy the hosted version as appropriate. See Change a runtime setting.
    4. Application Insights shows the failing dependency. Use the queries in Monitoring.

    Access denied between services

    Cause. A managed identity is missing a role, or a role assignment has not propagated yet. New assignments can take several minutes.

    Fix. Compare the assignments with Identity and roles. Wait a few minutes and retry before adding roles manually.
