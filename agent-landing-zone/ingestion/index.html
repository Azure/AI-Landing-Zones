    Ingestion and conversation uploads

    Foundry IQ provides the standard source-ingestion path. Conversation attachments and custom processing are separate capabilities that can require optional Agent App Ingestion.

    This page explains those boundaries. Deployment steps are in the Deploy full stack runbook. Source and index inputs are described in Deployment settings.

    1. Standard ingestion with Foundry IQ

    The default source is Azure Blob Storage, with FOUNDRY_IQ_PATTERN=azureBlob and container documents. Azure AI Search, which powers Foundry IQ, creates and manages the indexing pipeline for this knowledge source. It extracts content, splits it into smaller passages (chunks), generates embeddings (vectors used for similarity search) and populates an index used by the knowledge base.

    Agent App Ingestion is not required for this path. New Agent Application environments default to DEPLOY_INGESTION_CONTAINER_APP=false.

    Source documents belong in the configured Blob container and optional folder, not in a chat attachment. Search's ingestion identity needs access to storage and the configured extraction and embedding services. The default permission metadata is ["rbacScope"]. Ingestion permissions and the querying user's authorization remain separate requirements. Microsoft's Blob knowledge-source guide describes the managed pipeline and service requirements.

    Successful ingestion alone does not establish protected retrieval. The built-in UI/hosted native path forwards a separately delegated Search token. Ingestion must still record correct permissions and acceptance must prove allow/deny behavior. Application access describes the OBO contract.

    Foundry also supports native SharePoint options, including previews:

    Native option What happens to the content
    Foundry IQ indexedSharePoint source A service-managed pipeline copies and processes SharePoint content into a Search index. No Agent App Ingestion is required by the service.
    Foundry IQ remoteSharePoint source The knowledge base queries Microsoft 365 at retrieval time. It does not copy the SharePoint corpus into a landing-zone index. Retrieved text still reaches the agent and model.
    Foundry Agent Service SharePoint tool The agent calls a native tool backed by Microsoft 365 retrieval, outside the knowledge-base source list. It does not require the custom ingestion application.

    These product options are not all wired into Agent Application. The native indexed SharePoint path includes source registration, permission ingestion and delegated Search authorization. Remote retrieval and native tools need their own connection, consent and trusted delegated-user integration. Native tool calls require the user's identity, not application-only access. SharePoint explains the supported bindings and administrator prerequisites. Preview status is a governance consideration, not a reason to assume custom ingestion is required.

    The accelerator's ingestion-free validation accepts native Blob or an explicitly bound, independently populated Search index as its primary selection. Native indexed SharePoint is an additional configured knowledge source. Enabling it does not require Agent App Ingestion or replace the primary pattern setting. Other Microsoft product options are not automatically supported deployment selections in the accelerator.

    2. Conversation file uploads

    A chat attachment is processed for one conversation, not added to the shared native Blob corpus. This path requires Agent App Ingestion, its reachable endpoint and a compatible Search index. Alongside the default native Blob source, the additional conversation searchIndex source needs FOUNDRY_IQ_CONVERSATION_UPLOAD_ENABLED=true. The flag is invalid without the ingestion app.

    With DEPLOY_INGESTION_CONTAINER_APP=false, Agent App UI hides attachment controls and rejects server uploads and client preflight before resolving an ingestion endpoint or Dapr fallback. Setting it to true permits the upload path. Retrieval uses the built-in delegated Search route and native index permissions. Enabling processing does not grant access to uploaded content.

    The UI's attachment controls require authenticated access. Anonymous Copilot sessions cannot upload. The chat handler accepts PDFs, up to five files, 15 MiB per file and 25 MiB total. Hosted uploads require the UI's existing hosted conversation identifier. A text turn establishes it in the non-continuity hosted path. Continuity-enabled chat does not populate that upload identifier.

    The UI requires a valid object ID from its authenticated uploader context before calling ingestion. Ingestion stamps every chunk with that uploader in metadata_security_user_ids, an empty metadata_security_group_ids array, an empty metadata_security_rbac_scope and the conversation ID. The platform enables native permission filtering over these fields.

    Conversation scope uses the hosted backend's conversation namespace, not the local UI thread ID. The same identifier must reach the indexed upload and retrieval filter. Native Search authorizes the uploader from the delegated Search token and the ingested user ACL. The additional filter restricts results to the current conversationId. Neither a conversation ID nor an opaque hosted user/partition identifier grants document access.

    Missing required delegation or conversation scope stops retrieval. A configured upload source cannot be silently skipped to return only shared-corpus results, and a failed source cannot be retried without the user's credential. The conversation PDF reference describes source bindings. Application access describes the integrated identity path and consent requirements.

    3. Custom ingestion only when needed

    Agent App Ingestion is useful when the managed source does not meet processing requirements, or when conversation uploads or the application's custom SharePoint jobs are required. Its format-specific processing performs chunking and embedding generation and writes content to Search. An independent pipeline can instead populate a compatible index exposed through a Foundry IQ searchIndex source.

    The optional application's SharePoint connector uses Microsoft Graph application credentials and indexing/purge jobs. It copies content and permission metadata into Search. Permission synchronization and query-time enforcement still need validation.

    Every selected item's supported ACLs are reconciled on each SharePoint index run, even when content is unchanged, without re-downloading or embedding that content. Grants and revocations replace stored permissions on all affected documents and chunks. See SharePoint permission synchronization for scheduling, filter boundaries, inherited-permission support and recovery.

    It is separate from native SharePoint knowledge sources and the native Foundry tool. Its SHAREPOINT_* credentials are not the SHAREPOINT_REMOTE_* retrieval settings. Secrets belong in Key Vault.

    For the bundled Agent Application, DEPLOY_INGESTION_CONTAINER_APP selects the optional component through the Deploy full stack runbook, not a runtime-only edit. Existing environments retain their recorded selection. custom application definitions retain their declared components. Selection does not change retrieval bindings or document authorization. Omitting the application does not delete deployed resources, indexed documents or identity grants. Retirement needs separate authorization.

    Prepare the custom pipeline

    1. Deploy the optional application only for the required processing paths. Starting it can immediately run indexing and destructive maintenance work. Read Jobs & schedules before connecting it to a corpus.
    2. Supply APP_CONFIG_ENDPOINT in its process environment. Runtime configuration and Key Vault references are loaded through Azure credentials. A local Azure CLI login still needs data-plane RBAC and network access. Use Application settings for exact keys and effective-value checks rather than creating duplicate service-label values.
    3. Configure the target Search endpoint and compatible index, source storage, log storage and embedding deployment. The Blob indexer reads SEARCH_SERVICE_QUERY_ENDPOINT, STORAGE_ACCOUNT_NAME, DOCUMENTS_STORAGE_CONTAINER (default documents) and BLOB_PREFIX (default empty). Its index selection uses AI_SEARCH_INDEX_NAME when configured, otherwise SEARCH_RAG_INDEX_NAME.
    4. Add only the dependencies required by the selected format and source. PDFs, images and Office documents use the selected analysis service. Text, JSON, spreadsheets and transcripts have dedicated paths. See Document formats & images. SharePoint additionally needs Graph credentials and source definitions. NL2SQL needs metadata jobs and separate database configuration.
    5. Grant the ingestion workload only the required source read, target Search write, storage, model and secret access. Verify connectivity from the actual service, including private endpoints where configured.
    6. Process a small corpus and inspect per-file errors, confirmed indexed chunks, citations and allowed/denied-user retrieval before scheduling broader work.

    USE_DOCUMENT_INTELLIGENCE=false selects Content Understanding by default. MULTIMODAL=false keeps the additional figure extraction and captioning path off. Neither setting chooses the orchestrator's strategy or changes the native Foundry IQ source's processing configuration.

    An ingestion-maintained index can be attached to Foundry IQ as a searchIndex source on the same Search service. Registration does not populate it, repair its schema or reconstruct missing ACLs. Keep the index and embedding dimensions aligned with the source binding.

    Ingestion APIs and retrieval boundaries

    POST /document-chunking, POST /text-embedding and POST /ingest-documents have different JSON envelopes, not a common arbitrary file-upload contract. They require X-API-KEY, accepting DATA_INGEST_APP_APIKEY and its legacy INGESTION_APP_APIKEY alias. Keep the key in secret storage. Successful Azure SDK managed-identity access does not remove inbound API authentication.

    For direct ingestion, inspect each record's errors and confirmed indexedChunks. HTTP success for the envelope is not proof that every record was indexed. Use the API reference for payload details. The administrative dashboard and Monitoring & audit provide the operator view.

    Hosted Toolbox retrieval

    The separate preview POST /retrieve endpoint is not an ingestion API or the native Foundry IQ retrieve call. It remains unavailable with 503 until both HOSTED_RETRIEVAL_ENABLED and HOSTED_RETRIEVAL_INV_002_VALIDATED are enabled. Both default to false. The second is an operator attestation of the required isolated native-authorization validation, not a test the service runs or an attestation established by successful deployment.

    Before enabling it, configure Toolbox UserEntraToken passthrough, HOSTED_RETRIEVAL_TOKEN_AUDIENCE, native Search permission fields and the required user/service grants. Validate restricted users and negative cross-user and group cases. This existing authorization gate is separate from application evaluation.

    The route requires a validated delegated user bearer. The service uses its own credential for Search transport and forwards the user's token unchanged in x-ms-query-source-authorization. It accepts a query and bounded result count, not caller-supplied identity, groups or index selection. An API key or workload identity alone cannot replace the delegated user. See Application authentication and API reference for the token and response contracts.

    Native upload downloads repeat authorization through Search for the exact document, conversation and authenticated uploader before workload Blob access. A signed citation selector or known conversation ID is insufficient. Shared-source Blob/ADLS downloads instead use user-delegated Storage access. See protected citation downloads.

    For every path, acceptance includes a document that an allowed user can retrieve with its citation and that a denied user cannot retrieve. Source permissions, query-time enforcement and private-network connectivity require separate validation. Private Blob ingestion is covered in Network isolation.
