    How it works

    Agent Landing Zone connects deployment inputs, Azure infrastructure and application code through the Azure Developer CLI (azd). This page introduces those concepts for the Bicep/azd implementation, so you can understand what the deployment does without memorizing commands or parameters.

    A command-line interface (CLI) runs commands in a terminal. Bicep describes Azure resources as code; azd coordinates their creation and application deployment. Azure Blob Storage stores files, and Azure AI Search indexes content so the application can retrieve relevant passages. An application programming interface (API) lets code send requests to a service.

    An orchestrator coordinates model calls, retrieval and tools. The default Agent Application runs it in Foundry Agent Service with maf_lite, the supplied orchestration strategy (the code path that coordinates a turn). It has no administration panel and uses native Foundry IQ Blob ingestion, where Azure AI Search prepares Blob documents for retrieval.

    The sections below explain how that application and its infrastructure are prepared. The Deploy infra only and Deploy full stack runbooks provide the execution steps.

    How to read deployment settings

    A deployment parameter tells the template what to create or reuse, such as a private network or an existing hub. An azd environment groups the settings and deployment state for one deployment, such as development or production. With Bicep and azd, the runbooks use two ways to supply parameter values:

    Input form Source
    Uppercase input, such as NETWORK_ISOLATION The selected azd environment. The platform maps it to a template parameter or reads it in a deployment hook.
    Native parameter, such as modelDeploymentList The root main.parameters.json, inside parameters.<name>.value, for parameters without an environment-variable mapping.

    For example, NETWORK_ISOLATION=true selects private networking. Deployment inputs are resolved before provisioning. The platform combines them with the root parameter file to generate infra/main.parameters.json. The Deployment settings reference lists inputs and defaults; the Deploy infra only and Deploy full stack runbooks provide their application order.

    Application-specific runtime settings

    Runtime settings control an application's behavior and vary by application. Here they describe Agent Application, the supplied reference app. Its settings are usually stored in Azure App Configuration.

    Repository boundaries

    The platform repository coordinates infrastructure and application deployment. The Agent Application's runtime code lives in separate component repositories.

    Area Responsibility
    Infrastructure: platform infra/ Repository-owned Bicep source for Azure resources, identities and access. manifest.json → infra.source records the upstream AI Landing Zone source it incorporates.
    Platform integration: root files, scripts/ and config/ Selects the application, composes deployment parameters, configures provisioned services and coordinates deployment.
    Runtime component repositories Own Agent App UI, Agent App Orchestrator (strategies and tools), and optional Agent App Ingestion. The manifest identifies their repositories and source pins.

    The infra.source entry records the upstream version incorporated into this repository. Deployment uses the platform's own infra/ tree, which includes Agent Landing Zone changes.

    The manifest records a validated combination

    manifest.json records the platform release and each Agent Application component's repository, release tag and exact Git commit. A Git commit identifies an exact source revision; a tag is a readable label for a version. These identify the code versions validated together.

    The hooks fetch selected Container App components into sibling directories and verify their commits. Hosted image preparation fetches the pinned orchestrator separately. Deploying the reference app needs no repository forks.

    The Agent Application's app-definition.json also records component commits and is validated against the manifest. A modified combination needs its own integration validation. See Custom applications for repository customization and pinning rules.

    Parameters describe the environment

    The checked-in root main.parameters.json maps deployment inputs to infrastructure parameters. Values can be literals or references to the selected azd environment's variables. Inline defaults apply where declared; other unset inputs can use Bicep defaults.

    Before provisioning, the hooks resolve the application and hosting topology, apply environment inputs and generate infra/main.parameters.json for Bicep.

    Edit the source, not the generated output

    Use documented deployment inputs and the root parameter file. Do not edit infra/main.parameters.json; the next composition can overwrite it. See Deployment settings for inputs and defaults.

    An application definition describes the selected application's components and capabilities. The environment records that definition's id on first provision and rejects a different one later. This identifies the deployed application; it is not a Microsoft Entra ID application registration ID.

    Microsoft Entra ID handles sign-in and service identities in an organization's directory, called a tenant. An application registration describes a sign-in application to that service. Custom application selection therefore happens before the first provision.

    Hosting, orchestration strategy and ingestion selection are separate decisions. For example, choosing a hosted orchestrator does not select an ingestion path. The configuration and application definition must form a supported combination. The hosted runtime rejects unsupported strategies rather than silently switching strategy or host. The multimodal and nl2sql strategies are not supported by this host.

    azure.yaml connects azd to the lifecycle

    The root azure.yaml points azd at infra/ and registers PowerShell and shell lifecycle hooks. The hooks configure Azure services and coordinate application deployment.

    Stage What the platform does
    Before azd up (preup) Validates the application definition and checks that it matches the environment's recorded application.
    Before provisioning (preprovision) Resolves application selection and topology, composes infrastructure parameters and runs preflight checks.
    After provisioning (postprovision) Configures Azure services, reconciles application access and publishes runtime settings and outputs.
    Before deployment (predeploy) Checks infrastructure readiness and the recorded application, validates topology and required connectivity, then coordinates the selected application deployments.

    azd provision includes service configuration through its post-provision hook. Some Container Apps initially contain placeholder images; azd deploy replaces them with the selected application code.

    Container App deployment builds verified component code through each component's azure.yaml. Hosted orchestration uses the prepared image described below. Custom applications supply their own definitions and projects for deployment.

    App Configuration carries runtime settings

    Deployment inputs describe what to create. Runtime settings describe how applications use the resulting services.

    Provisioning and configuration publish settings to Azure App Configuration under the agent-lz label. The Agent Application loaders also select other labels, which can affect which setting takes precedence. Bootstrap values such as the store endpoint must be available before remote configuration can load. Secrets belong in Key Vault and are referenced rather than copied into checked-in settings.

    The same label is used across environments, so separation depends on distinct configuration, identities and data, as described in Environment boundaries. Local .azure/ state is private deployment state, not a source-controlled input file. Child workspaces receive copies and need the same protection.

    See Deployment settings for setting names, sources and reload requirements.

    Why hosted agents need image preparation

    A Foundry hosted agent needs an immutable image before its agent version can be deployed. That creates a bootstrap dependency on the registry and Foundry resources.

    An image digest identifies the built container image by its content. It is not a source commit or a mutable image tag.

    1. Infrastructure prerequisites. Initial provisioning creates and configures the required Azure services and access rules.
    2. Image preparation. The script builds the pinned orchestrator and its hosted entrypoint image, recording the digest and build details.
    3. Deployment metadata. A further provision records the prepared digest and configuration for the deployment hook.
    4. Application deployment. Deployment creates the hosted agent version and deploys the other selected application components.

    Image preparation does not start the agent, and provisioning does not create the running data-plane agent version. Deploy-only reuses a compatible prepared image rather than rebuilding changed orchestrator source.

    The same source pins do not guarantee the same image digest when images are built independently. If a promotion process requires the identical image, its digest and registry availability need separate preservation and verification.

    The Deploy full stack runbook provides execution steps. For strategy eligibility and image behavior, see Agent hosting.

    From understanding to deployment

    The planning references explain deployment design, sizing and cost. For execution, the named runbooks are Deploy infra only or Deploy full stack. Those runbooks contain the prerequisites, topology-specific sequence and validation steps.
