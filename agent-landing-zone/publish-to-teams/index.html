    Publish to Teams and Microsoft 365 Copilot

    Objective

    Publish an agent already hosted in Microsoft Foundry to Teams and Microsoft 365 Copilot. Start with a tested agent in a private-network Foundry project, then use its endpoint, identity and version throughout this runbook. The agent can be part of your own application.

    You will create a Bot Service resource, enable channel access and publish the agent's app listing. These are manual post-deployment tasks; the landing zone template does not perform them.

    What you'll have after this runbook

    Your existing Foundry agent available in Teams and Microsoft 365 Copilot, with authenticated messages delivered through Azure Bot Service.

    This channel path is not private end to end

    Teams and Microsoft 365 Copilot deliver messages to a public HTTPS Activity endpoint, restricted to Microsoft channel source IPs and requiring authentication. They do not use the Foundry private endpoint.

    If your organization requires no public agent ingress, do not use this publication path.

    Conversation path

    1. Teams or Microsoft 365 Copilot uses Microsoft's managed Azure Bot Service.
    2. Bot Service calls the public HTTPS Activity endpoint, with authentication and Microsoft channel source IP filtering. This is not Private Link.
    3. The hosted agent receives the authenticated messages. Foundry and Bot Service retain public network access disabled; the Activity route is the scoped exception.

    Publication setup and later changes

    1. The admin workstation connects through VPN or the private network.
    2. The Foundry project API is reached through its private endpoint to configure publication. This is separate from conversation traffic.

    Open full-size diagram

    The diagram's dashed path is for publication setup and later changes, not for Teams conversations.

    The Bot Service box represents Microsoft's managed channel service, not a bot hosted inside your VNet. Its resource uses publicNetworkAccess: Disabled, as Microsoft's Foundry publishing procedure prescribes. That resource setting does not make Teams/M365 delivery private: the channel service calls the public Foundry Activity route shown above.

    When to use

    Use this runbook after the hosted agent works and you need Teams or Microsoft 365 Copilot distribution while Foundry public network access remains disabled. For a Copilot Studio private relay instead, use Connect Copilot Studio.

    Microsoft calls this a source IP-filtered Activity Protocol public endpoint: a public endpoint for the messaging route, restricted by the source IP addresses of Microsoft's channel services. See the Foundry REST publishing flow.

    Step 3 sets activity.enable_m365_public_endpoint=true to enable that specific exception. Foundry and Bot Service keep public network access (PNA) disabled; management APIs and other agent protocols remain private.

    Path Network access
    Bot Service to the Activity endpoint Public HTTPS, with Microsoft-managed source IP filtering and authentication. Not Private Link.
    Connected workstation to the Foundry project API Private endpoint, for publication setup and later changes.

    Microsoft manages the allowed source ranges. You do not open public ingress on your VNet. An allowed source IP still needs valid authentication and authorization; public does not mean anonymous.

    During setup, your connected workstation calls the Foundry project API through the private endpoint to read the agent configuration, enable Activity and select the tested version. The private endpoint carries those requests; it is not the resource you are configuring.

    Prerequisites

    • Agent: Have a working hosted agent in a Foundry project, with its own agent identity, a stable endpoint and a version you have tested. If you still need to deploy an application, start with the Deploy full stack runbook or Custom applications, then return here.
    • Network access: Run the commands from a VNet-connected host that resolves and reaches the Foundry project's private endpoint. This procedure requires Foundry PNA to be disabled. For a project with public access enabled, use the Foundry portal publishing procedure.
    • Tools: Install Azure CLI, Bicep CLI and PowerShell 7.4 or later. Run Steps 1-4 in the same PowerShell session; later blocks use variables set by earlier ones.
    • Azure permissions: You need Foundry User on the project, plus Azure Bot Service Contributor Role and permission to create deployments in the target resource group. Resource-group Contributor covers both bot creation and deployment. A subscription administrator must register Microsoft.BotService if it is not already registered.
    • Microsoft 365 access: Use member accounts in the same tenant as Foundry, with access to Teams and Microsoft 365 Copilot and app policies that allow the agent. Guest accounts cannot call these agents. Tenant-wide publication needs approval from a Microsoft 365 administrator.

    Licensing and costs

    To use the agent in Microsoft Copilot Chat, users need an eligible Microsoft 365 subscription. The Microsoft 365 Copilot add-on is optional:

    • With the add-on: No additional Microsoft 365 usage charge for using this agent.
    • Without the add-on: Access to shared tenant data, such as SharePoint or Copilot connectors, can incur usage-based charges in Copilot Credits.

    In both cases, Azure costs are separate: the license does not cover Foundry model usage, agent hosting or other Azure services. See licensing and costs for custom engine agents.

    Approve the data flow first

    Obtain your organization's approval before sending data through this channel. Microsoft 365 processes publishing metadata and conversations under its own compliance and data-residency commitments. Validate how the agent authenticates users and enforces data permissions in both Teams and Microsoft 365 Copilot before rollout.

    The Agent Application UI performs a separate delegated Search exchange. Channel publication does not automatically reproduce that credential path or prove per-user document authorization. Validate the channel's supported delegation before admitting protected data.

    Procedure

    Complete Steps 1-4 in order, then run all client and configuration checks under Validation. Keep the backup and publication results for rollback.

    Step 1: Select the agent and save its configuration

    In the Azure portal, collect the subscription ID, resource group name, Foundry resource name and project name. Then open the agent in Foundry and record its name and tested version. Use these values for the agent you want to publish.

    Expand the block below, replace every placeholder and run it on the connected host. The commands check the agent's identity and save its configuration before you change it. Keep Shared for the initial pilot. Tenant-wide access requires the separate approval described below before enabling it.

    PowerShell: select the target and save a backup 
    $ErrorActionPreference = "Stop"
$PSNativeCommandUseErrorActionPreference = $true

$subscriptionId = "<subscription-id>"
$resourceGroup = "<foundry-resource-group>"
$foundryName = "<foundry-resource-name>"
$projectName = "<foundry-project-name>"
$agentName = "<agent-name>"
$agentVersion = "<tested-agent-version>"
$botName = "<globally-unique-bot-name>"
$publishScope = "Shared"

az login
az account set --subscription $subscriptionId
$tenantId = az account show --query tenantId --output tsv
az account show --query "{subscription:id,tenant:tenantId}" --output table

$pna = az cognitiveservices account show --name $foundryName `
    --resource-group $resourceGroup --query properties.publicNetworkAccess --output tsv
if ($pna -ne "Disabled") { throw "This runbook requires Foundry PNA Disabled." }

$work = Join-Path $HOME ("teams-publication-" + (Get-Date -Format "yyyyMMdd-HHmmss"))
New-Item -ItemType Directory -Path $work | Out-Null
Set-Location $work

$projectEndpoint = "https://$foundryName.services.ai.azure.com/api/projects/$projectName"
$agentUri = "$projectEndpoint/agents/$([uri]::EscapeDataString($agentName))"
$token = az account get-access-token --resource https://ai.azure.com `
    --query accessToken --output tsv
$headers = @{ Authorization = "Bearer $token" }
Remove-Variable token

$agent = (Invoke-WebRequest -Uri "${agentUri}?api-version=v1" `
    -Headers $headers).Content | ConvertFrom-Json -AsHashtable
if (-not $agent.instance_identity.client_id -or -not $agent.agent_endpoint) {
    throw "The agent needs a unique identity and stable endpoint. Stop before publishing."
}
$agent | ConvertTo-Json -Depth 100 | Set-Content agent-before.json
@{
    subscriptionId = $subscriptionId
    tenantId = $tenantId
    resourceGroup = $resourceGroup
    foundryName = $foundryName
    agentUri = $agentUri
    botName = $botName
} | ConvertTo-Json | Set-Content target.json
$agent.agent_endpoint | ConvertTo-Json -Depth 100
"Working folder: $work"

    Expected result: The commands complete without errors and display the intended tenant and subscription, the endpoint configuration and a working-folder path. Record that path. Keep target.json and agent-before.json in that folder, outside source control; neither file contains the bearer token.

    Before continuing, choose who can use the agent. The block starts with $publishScope = "Shared", which is the recommended pilot scope. Your choice controls both catalog visibility and permission to call the agent:

    $publishScope Who can call the agent Store visibility
    Shared Only identities with the required Foundry permissions can invoke it, through BotServiceRbac. The publisher finds it under Your agents and can share the link with authorized testers. Publishing approval is not required.
    Tenant Everyone in the Foundry tenant can invoke it, through BotServiceTenant. It appears under Built by your org after Microsoft 365 admin approval.

    For tenant-wide distribution, set $publishScope = "Tenant" in the same session before Step 3, and only after your organization approves that access. For a Shared pilot, ask an administrator to grant selected testers Foundry Agent Consumer at the agent scope. Grant this access before sharing the app link.

    If the agent identity check fails

    Stop and have the agent owner supply a supported agent identity and stable endpoint before retrying this runbook. Bot Service needs the agent identity's client ID (instance_identity.client_id), not the project's managed identity or an application registration belonging to another client.

    Step 2: Create the bot and Teams channel

    Complete the three sections below in order. This creates a separate Bot Service resource and its Teams channel; the same channel also serves Microsoft 365 Copilot. You do not need to add a bot runtime or modify the landing zone template.

    1. Check Bot Service provider registration

    Run this command in the PowerShell session from Step 1:

    az provider show --namespace Microsoft.BotService --query registrationState --output tsv

    Expected result: The provider state is Registered. If it is not, ask a subscription administrator to run az provider register --namespace Microsoft.BotService --wait, then check again. Do not deploy the bot until registration is complete.

    2. Save bot-service.bicep in the working folder

    Create a file named bot-service.bicep in the $work folder created in Step 1, and paste the following template into it:

    param botName string
param displayName string
param msaAppId string
param tenantId string
param endpoint string

resource bot 'Microsoft.BotService/botServices@2022-09-15' = {
  name: botName
  kind: 'azurebot'
  location: 'global'
  sku: {
    name: 'F0'
  }
  properties: {
    displayName: displayName
    endpoint: endpoint
    msaAppId: msaAppId
    msaAppTenantId: tenantId
    msaAppType: 'SingleTenant'
    publicNetworkAccess: 'Disabled'
  }
}

resource teams 'Microsoft.BotService/botServices/channels@2021-03-01' = {
  parent: bot
  name: 'MsTeamsChannel'
  location: 'global'
  properties: {
    channelName: 'MsTeamsChannel'
  }
}
    3. Deploy the bot and verify its network setting

    Replace <agent-display-name> with the name users should see. Run the commands from $work to deploy the saved template into the Foundry resource group.

    $displayName = "<agent-display-name>"
$activityEndpoint = "$agentUri/endpoint/protocols/activityProtocol"

az deployment group create --resource-group $resourceGroup `
    --name "teams-bot" --template-file bot-service.bicep `
    --parameters botName=$botName displayName="$displayName" `
        msaAppId=$($agent.instance_identity.client_id) tenantId=$tenantId `
        endpoint=$activityEndpoint --output none

$botServiceId = az bot show --name $botName --resource-group $resourceGroup `
    --query id --output tsv
az resource show --ids $botServiceId --api-version 2022-09-15 `
    --query "properties.{endpoint:endpoint,pna:publicNetworkAccess}" --output json

    Expected result: The bot's endpoint matches the agent's activityProtocol URL, and its network setting is "pna": "Disabled". The bot uses the agent's identity; you do not need a client secret, public VNet ingress or a custom connector.

    Step 3: Enable the source-IP-filtered public Activity route

    Run the block below to enable the public HTTPS Activity exception, apply the Bot Service authorization scheme for your chosen audience and send traffic to the tested agent version. The block reads the current configuration so it can preserve the existing protocols and non-Bot authorization schemes. It also checks for Foundry's default Entra authorization. If you changed that configuration, review the endpoint authorization settings before proceeding.

    Preserve access for existing consumers

    The API replaces the submitted protocol configuration and authorization array. Keep the protocols and authorization schemes your agent already uses, such as responses, invocations and Entra. Removing them can break other clients. Pinning the version also affects all consumers of the stable endpoint, not just Teams and Copilot. Avoid concurrent agent configuration changes.

    PowerShell: enable Activity and pin the tested version 
    if ($publishScope -notin @("Shared", "Tenant")) { throw "Choose Shared or Tenant." }
$agent = (Invoke-WebRequest -Uri "${agentUri}?api-version=v1" `
    -Headers $headers).Content | ConvertFrom-Json -AsHashtable
$protocols = $agent.agent_endpoint.protocol_configuration
if (-not $protocols) { throw "Review the agent's existing protocols before continuing." }
$activity = $protocols.activity
if (-not $activity) { $activity = @{} }
$activity.enable_m365_public_endpoint = $true
$protocols.activity = $activity

$botScheme = if ($publishScope -eq "Tenant") { "BotServiceTenant" } else { "BotServiceRbac" }
$schemes = @($agent.agent_endpoint.authorization_schemes |
    Where-Object { $_.type -notin @("BotServiceRbac", "BotServiceTenant") })
$schemes += @{ type = $botScheme }
if ("Entra" -notin $schemes.type) { throw "Review missing Entra authorization before continuing." }

$patch = @{
    agent_endpoint = @{
        protocol_configuration = $protocols
        authorization_schemes = $schemes
        version_selector = @{
            version_selection_rules = @(
                @{ type = "FixedRatio"; agent_version = $agentVersion; traffic_percentage = 100 }
            )
        }
    }
} | ConvertTo-Json -Depth 100

Invoke-RestMethod -Method Patch -Uri "${agentUri}?api-version=v1" `
    -Headers $headers -ContentType "application/merge-patch+json" -Body $patch |
    Out-Null

    Expected result: The update completes without errors and prints no output. You will check the final configuration under Validation.

    Step 4: Publish the app

    This step submits the listing directly to the catalogs. If your organization requires package review before submission, use the REST package-download procedure rather than publishing directly.

    Replace the placeholders below with approved listing details, including your organization's HTTPS website, privacy statement and terms of use. These details are visible to users; do not include secrets or sensitive information.

    PowerShell: publish to Teams and Microsoft 365 Copilot 
    $publishRequest = @{
    agentDisplayName = $displayName
    botServiceArmId = $botServiceId
    publishScope = $publishScope
    publishAsAutopilot = $false
    appVersion = "1.0.0"
    shortDescription = "<short-description>"
    fullDescription = "<full-description>"
    developerName = "<organization-name>"
    developerWebsiteUrl = "https://<organization-domain>"
    privacyUrl = "https://<organization-domain>/privacy"
    termsOfUseUrl = "https://<organization-domain>/terms"
}
$body = $publishRequest | ConvertTo-Json -Depth 10
$body | Set-Content publish-request.json
$result = Invoke-RestMethod -Method Post `
    -Uri "${agentUri}/microsoft365/publish?api-version=v1" `
    -Headers $headers -ContentType "application/json" -Body $body
$result | ConvertTo-Json -Depth 20 | Set-Content publish-result.json
$result

    Expected result: The response contains titleId. If you selected Tenant, ask a Microsoft 365 administrator to approve the request in Microsoft 365 admin center > Agents > Requests. Approval is required before tenant-wide discovery, and app policies can still restrict availability.

    App version versus agent version

    appVersion is the version of the store listing. Increase it when you republish metadata or change publication scope. $agentVersion selects the running agent version; changing that version does not require republishing the listing.

    Optional: inspect a copy of the published app package

    To inspect or retain the package after direct publication, run this block in the same session. It reuses the publication request:

    Invoke-WebRequest -Method Post -Uri "${agentUri}/microsoft365/zip?api-version=v1" `
    -Headers $headers -ContentType "application/json" -Body $body -OutFile appPackage.zip

    Extract the ZIP and review its manifest and icons with the package inspection checklist. Keep the generated IDs and agent sections unchanged.

    The download call does not submit the app to the catalogs, but it can update the agent's publishing configuration and requires agent write permission. Downloading this copy does not require uploading it again.

    Validation

    Returning later or using a new PowerShell session?

    Use this block only to resume verification or maintenance after the bot has been created. Run it on the connected host, replacing <saved-working-folder> with the path recorded in Step 1. It restores the connection variables and gets a fresh token without recreating the bot or republishing the app.

    $ErrorActionPreference = "Stop"
$PSNativeCommandUseErrorActionPreference = $true
Set-Location "<saved-working-folder>"
$target = Get-Content target.json -Raw | ConvertFrom-Json -AsHashtable
$resourceGroup = $target.resourceGroup
$foundryName = $target.foundryName
$agentUri = $target.agentUri

az login --tenant $target.tenantId
az account set --subscription $target.subscriptionId
$token = az account get-access-token --resource https://ai.azure.com `
    --query accessToken --output tsv
$headers = @{ Authorization = "Bearer $token" }
Remove-Variable token
$botServiceId = az bot show --name $target.botName --resource-group $resourceGroup `
    --query id --output tsv

    After publication, open the agent in both clients. For Shared, sign in with the publishing account. For Tenant, wait for admin approval and find the agent under Built by your org.

    Client Open the agent
    Teams Open Apps, find the agent, add it and open its chat.
    Microsoft 365 Copilot Open the Agents area, find the agent in the agent store and add it. For Shared, look under Your agents.

    Complete these checks in each client before making the agent available to users:

    1. Complete any sign-in prompt. Send a greeting, a representative workload question and a follow-up. Confirm that the answers use the expected tools and knowledge sources.
    2. For a Shared pilot, test with an authorized user and a tenant member who lacks agent permission. The second user must be denied. Use member accounts, not guests. With Tenant, all tenant members are authorized to call the agent; test protected-data restrictions separately as described next.
    3. If the agent handles protected data, test with identities that should and should not access that data. Confirm the intended restrictions in both clients, regardless of publication scope.

    Then return to the connected host and run the final configuration check:

    PowerShell: verify the endpoint and both PNA settings 
    $after = Invoke-RestMethod -Uri "${agentUri}?api-version=v1" -Headers $headers
$after.agent_endpoint | ConvertTo-Json -Depth 30
az cognitiveservices account show --name $foundryName --resource-group $resourceGroup `
    --query properties.publicNetworkAccess --output tsv
az resource show --ids $botServiceId --api-version 2022-09-15 `
    --query properties.publicNetworkAccess --output tsv

    Expected result: The tested version receives 100% of traffic. The original protocols and Entra authorization are preserved, activity.enable_m365_public_endpoint is true, and the Bot Service scheme matches your publication scope. Both PNA values must remain Disabled.

    Channel limitations

    Published agents do not support streaming responses or citations. File uploads and image generation are not supported in Microsoft 365 Copilot, although they are available in Teams. Test the capabilities your agent uses in each client and review the Foundry publishing limitations before rollout.

    Channel support does not add upload or image-generation handlers to the supplied Agent Application. Its images and voice contract and protected-retrieval authorization requirements still apply.

    Update or stop publication

    Use the following actions to maintain the published agent. If your PowerShell session ended or its token expired, resume the session before running the maintenance commands.

    Task Action
    Release a new runtime version Test the version, then follow the REST API tab in the active-version instructions from the connected host. Keep the existing bot and listing.
    Roll back agent behavior Use the same REST instructions to select the previous tested version. This changes the version for every consumer of the stable endpoint.
    Change the listing name, descriptions or URLs Edit publish-request.json, increase appVersion and run Update listing metadata below. Keep botServiceArmId and publishScope unchanged for a metadata-only update.
    Check publication after redeployment Recheck the active version, Activity exception and authorization, then repeat Validation. The landing zone template does not manage this manual configuration.
    Update listing metadata

    Open publish-request.json in the saved working folder. Update the listing details, increase appVersion and review the entire request before running the block below. A Tenant update can require renewed admin approval.

    $body = Get-Content publish-request.json -Raw
$result = Invoke-RestMethod -Method Post `
    -Uri "${agentUri}/microsoft365/publish?api-version=v1" `
    -Headers $headers -ContentType "application/json" -Body $body
$result | ConvertTo-Json -Depth 20 | Set-Content publish-result.json
$result

    Troubleshooting

    Symptom What to check or do
    A project GET or PATCH fails or times out. Check private DNS and connectivity, the selected tenant, the Foundry User role and the token audience (https://ai.azure.com). If the token expired, resume the session. Do not enable PNA to bypass the error.
    The bot deployment is denied. Check Microsoft.BotService registration, bot and deployment permissions, and any Azure Policy denial.
    The agent is missing from either client. Check the signed-in account, publication scope, admin approval and app policies. Refresh the store or sign out and back in; catalog caching can delay discovery.
    Activity returns 403 NetworkAccessDenied. Check that the Activity exception is enabled and test through Teams or Copilot. A public curl request from an arbitrary IP remains blocked by design.
    A user can open the app but receives an authorization error. Check that the user is signed in to the Foundry tenant and, for Shared, has Foundry Agent Consumer access. Do not switch to Tenant just to remove the error.
    The Teams sign-in card opens, but its redirect page does not load. Ask the network administrator to allow outbound HTTPS (TCP 443) to *.azureml.ms from the user's network, then retry sign-in.
    The agent replies, but tools or retrieval fail. Check runtime identity permissions, data authorization and outbound access. Trace the failing request through Teams or Copilot to verify identity propagation in that client.
    A conversation is stuck or returns no tool output found. In Teams, send /foundry_new_preview; in Copilot, start a new chat with the agent. Previous conversation context cannot be restored after a reset.
    Publication returns version already exists. Increase appVersion and submit the listing again. Do not change the runtime version to fix a listing-version error.

    For other errors, use Foundry publishing troubleshooting and published-agent authorization.

    Rollback

    1. For a runtime-only regression, select the previous tested version using the active-version REST instructions. This affects every consumer of the stable endpoint. Repeat Validation before reopening access.
    2. To withdraw the newly introduced publication, disable the Activity exception using the block below, then ask the Microsoft 365 administrator to block or remove its listing from both catalogs. If other approved channel consumers already use this exception, coordinate withdrawal rather than interrupting their access.

    To stop channel access from both clients, run the block below. It disables only the public Activity exception, leaving the other endpoint protocols and their private access unchanged. Keep Foundry PNA disabled.

    Stop Teams and Copilot access

    The commands read the current protocol configuration and change only the Activity exception:

    $current = (Invoke-WebRequest -Uri "${agentUri}?api-version=v1" `
    -Headers $headers).Content | ConvertFrom-Json -AsHashtable
$protocols = $current.agent_endpoint.protocol_configuration
if (-not $protocols.activity) { throw "No Activity configuration found; review the endpoint." }
$protocols.activity.enable_m365_public_endpoint = $false
$disable = @{ agent_endpoint = @{ protocol_configuration = $protocols } } |
    ConvertTo-Json -Depth 100
Invoke-RestMethod -Method Patch -Uri "${agentUri}?api-version=v1" `
    -Headers $headers -ContentType "application/merge-patch+json" -Body $disable |
    Out-Null

    After the update, confirm that new requests from Teams and Copilot no longer reach the agent. Ask the administrator to block or remove the app from the catalogs. Uninstalling the app alone does not revoke endpoint access. Do not delete shared Foundry resources or restore an old backup over later configuration changes.

    For full pilot retirement, remove only the newly created bot and pilot-only agent-scoped grants after their owners confirm no other consumers depend on them. Retain the Foundry agent, its identity and data. If reverting listing metadata rather than withdrawing access, use the previous approved metadata with an increased appVersion; do not reuse an already published version.
