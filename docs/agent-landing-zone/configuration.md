# Deployment settings

Use this reference to configure provisioning with Bicep or Terraform.
[Deployment choices](planning.md) explains the decisions and
[Network design](network-isolation.md) explains connectivity.
For commands and execution order, choose a
[deployment guide](index.md#infrastructure-and-application).

Application resource requirements remain here because they affect provisioning.
Functional behavior, effective runtime values and reloads belong in
[Agent Application](application.md) and [Application settings](application-settings.md).
Read individual nonsecret keys rather than dumping whole environments.

## Deployment inputs

| Kind | Where it belongs | How to use it |
| --- | --- | --- |
| Mapped environment input | The selected `azd` environment. | Use the documented variable name. Tables below give its default or condition. |
| Native root parameter | `parameters.<name>.value` in root `main.parameters.json`. | Use typed JSON. A native parameter does not automatically have an environment mapping. |
| Generated provider input | Bicep's `infra/bicep/main.parameters.json` or Terraform's `infra/terraform/main.tfvars.json`. | Read for diagnosis, never edit resolved values as the source of a change. |
| Generated metadata or script state | Provisioning outputs, App Configuration or local deployment records. | Let the owning workflow produce it. See [generated values](#generated-values-and-script-state). |
| Application runtime setting | Normally App Configuration under `agent-lz`. | Follow its [application guide](application-settings.md), including ownership and reload requirements. |

Both providers resolve the root inputs before provision. Bicep's tracked seed
is regenerated by the hooks. Terraform's input is ignored by Git. Its ignored
`infra/shared/main.parameters.json` is a preflight diagnostic artifact,
**never a Terraform deployment input**. Do not edit or commit resolved values
in these files or generated `.azure/` inputs.

Keep booleans, numbers, arrays and objects as their native JSON types.
For example, the root parameter `allowedIpRanges` takes an array.
There is no implied `ALLOWED_IP_RANGES` environment binding.
Retain the same reviewed root document on every authorized runner.

## Terraform backend settings

Use an existing Azure Storage account and container outside every workload
resource group. Backend settings are separate from workload parameters:

| Variable | Required value or default |
| --- | --- |
| `TF_STATE_RESOURCE_GROUP` | Backend storage account's resource group |
| `TF_STATE_STORAGE_ACCOUNT` | Existing storage account name |
| `TF_STATE_CONTAINER` | Existing state container name |
| `TF_STATE_SUBSCRIPTION_ID` | Defaults to `AZURE_SUBSCRIPTION_ID` |
| `ARM_ENVIRONMENT` | Canonical `public`, `usgovernment` or `china`; qualified from CLI metadata or explicitly selected for process credentials |

The state key is `agent-landing-zone/${AZURE_ENV_NAME}.tfstate`.
AzureAD Blob authentication requires account **Reader** for metadata and
container **Storage Blob Data Contributor**. The workload does not bootstrap
the backend or include it in `azd down`.

Native azd disables state locking. Shared and production environments require
one authorized writer with queued, non-canceling execution per actual state
identity. This is an access/execution control, not backend locking. See the
[single-writer policy](deploy-terraform-infra-only.md#state-protection).
Follow [backend preparation](deploy-terraform-infra-only.md#step-3-prepare-remote-state-outside-the-workload)
for setup commands.

The adapter records the backend binding on first use before persisting its
settings and verifies it thereafter. A clean runner needs the original private
backend, group and application/environment records, not reconstructed files.
The provider selected in root `azure.yaml` applies to the checkout, not
independently to each azd environment.

### Azure cloud

The adapter generates the `azureCloud` context and passes the canonical
`ARM_ENVIRONMENT` into the backend:

| Cloud | Storage DNS suffix |
| --- | --- |
| `public` | `core.windows.net` |
| `usgovernment` | `core.usgovcloudapi.net` |
| `china` | `core.chinacloudapi.cn` |

CLI authentication must match the selected subscription and active CLI cloud.
Process credentials require an explicit cloud; any azd-store and process
values must agree. Preprovision persists the qualified cloud before native
backend initialization. The hooks do not change global cloud or authentication
settings.

## Environment boundaries

DEV, TEST and PROD need separate azd environments and resource groups.
Separate subscriptions strengthen administrative and quota boundaries.
Permissions, identities and dedicated stores enforce the following boundaries.

| Boundary | Keep separate |
| --- | --- |
| Target and deployment access | Resource group/subscription, azd environment and environment-scoped deployment identity. DEV must not deploy to PROD. |
| Runtime access | Component identities, grants and Entra registrations, or explicitly separated callbacks and consent. |
| Configuration and secrets | App Configuration store/endpoint and Key Vault. The `agent-lz` label is shared by convention, not an environment separator. |
| Data | Sources, indexes, conversation/history stores and retention. Use approved test data instead of copying production documents. |
| Network and builds | DNS, routes, private endpoints and a connected runner. An ACR build pool does not connect the deployment host. |

Approved nonsecret inputs can be version-controlled. An `environments/`
folder is not loaded automatically; its settings need explicit application.
Local `.azure` contains private deployment state, which hooks copy to child
projects. Those workspaces need the same protection and cannot safely be
copied between DEV, TEST and PROD.

## Deployment parameters

### Resource naming

[Resource naming](resource-naming.md) explains defaults, overrides and name
stability. Names resolve before the first provision; later changes can create
new resources instead of updating existing ones.

### Resource group destinations

This **Agent azd** interface is shared by the product's Bicep and integrated
Terraform paths using the compatible components pinned by the platform
manifest. For direct shared-module use or portal deployment, follow those
implementations' input references.

New environments use three resource groups by default: Foundry/grounding,
application and workload networking. Existing environments keep their mapping.
All workload destinations must be in `AZURE_SUBSCRIPTION_ID`. Equal names are
valid: one, two or three distinct groups can express the same three logical
destinations. These inputs do not enable services, change network isolation or
create a platform hub; existing BYO VNet, DNS and hub settings still apply.

| Variable | Default | Purpose |
| --- | --- | --- |
| `AZURE_RESOURCE_GROUP` | `rg-<environment-name>` | Foundry and grounding destination, and the native azd root deployment group. An explicitly supplied name is preserved. |
| `AZURE_APP_RESOURCE_GROUP` | `<AZURE_RESOURCE_GROUP>-app` | Application destination: Container Apps, registry, App Configuration, Key Vault, application Cosmos DB and monitoring. |
| `AZURE_NETWORK_RESOURCE_GROUP` | `<AZURE_RESOURCE_GROUP>-network` | Destination for workload-owned network resources. Existing network/private-endpoint overrides retain their own contract. |
| `CREATE_RESOURCE_GROUPS` | `true` for new environments | Strict boolean (`true` or `false`): allows creating missing additional destination groups. Set `false` to require pre-created additional groups. Does not disable azd's normal root-group creation. |

The hook saves these defaults in the selected azd environment before provision.
For long custom root names, generated names include a stable hash and suffix
within Azure's 90-character limit. These are first-run defaults, not automatic
changes to existing environments.

Set destinations **before first provision**. For three pre-created groups:

```bash
azd env set AZURE_RESOURCE_GROUP rg-ai
azd env set AZURE_APP_RESOURCE_GROUP rg-app
azd env set AZURE_NETWORK_RESOURCE_GROUP rg-net
azd env set CREATE_RESOURCE_GROUPS false
```

For two groups, set `AZURE_NETWORK_RESOURCE_GROUP` to `rg-ai` to keep networking
with Foundry, or `rg-app` to keep it with the application.
For one group, explicitly select the same name for all destinations:

```bash
azd env set AZURE_RESOURCE_GROUP rg-workload
azd env set AZURE_APP_RESOURCE_GROUP rg-workload
azd env set AZURE_NETWORK_RESOURCE_GROUP rg-workload
```

With `false`, a missing additional destination fails before services are
provisioned. With `true`, existing groups are reused without
changing their tags or location; only missing additional groups are created.

The additional destinations are application and network; azd manages creation
of the Foundry/root group through its normal lifecycle.
New additional groups do not receive the `azd-env-name` tag.

Run the normal product-root lifecycle: each `azd provision` coordinates the
selected provider across the configured destinations. Bicep uses its
resource-group-scoped root and scoped modules; Terraform uses its repository-owned
composition. Do not replace the lifecycle with three manual deployments.
Hosted image preparation remains part of application deployment.

#### Resource group permissions

- **Existing groups:** Contributor on each target covers resource management
  and `Microsoft.Resources/deployments/*`, not RBAC grants or data access.
  Splitting existing groups does not itself require subscription Owner or
  subscription-scope deployment permission.
- **Creating missing groups:** `CREATE_RESOURCE_GROUPS=true` additionally needs
  `Microsoft.Resources/subscriptions/resourceGroups/write` at subscription
  scope. A scoped custom role can grant that action; subscription Contributor
  is broader, not a universal prerequisite.
- **RBAC:** the deploying identity needs
  `Microsoft.Authorization/roleAssignments/write` at each assignment scope,
  for example through Role Based Access Control Administrator, subject to its
  conditions. Creating a group does not automatically grant this access.
- **Service configuration:** keep the required Foundry, Search, App
  Configuration, Key Vault and other service-specific data-plane roles.
  Management-plane Contributor does not replace them. External network/DNS
  resources require their owners' scoped permissions.

Resource-group Contributor and scoped RBAC administration do not grant Entra
directory reads; for platform-output client-ID discovery, restricted automation
can instead supply `AGENTLZ_COMPONENT_IDENTITIES` as a nonsecret JSON map of
Container App component names to pre-resolved managed-identity client IDs,
without granting broad directory rights.

The workflow records the mapping with the environment and uses the deploying
identity's permissions. Preserve that mapping for provisioning, deployment
and recovery.

After partial failure, repair the cause and
retry with the same destinations. Do not delete groups as automatic rollback.
Review every destination and shared dependency before any
[environment removal](deploy-full-stack.md#remove-an-environment).

For **Bicep**, the `predown` guard blocks split-group `azd down`; arrange
owner-reviewed, separately authorized cleanup.
For **Terraform**, the guard verifies the original common group binding,
`terraform-resource-groups.json` and `terraform-backend.json`, then permits
native state-scoped destroy across recorded owned/BYO groups. It rejects
missing records or retargeted groups/backend settings. See
[Terraform removal](deploy-terraform-infra-only.md#remove-the-foundation).

### Values set by azd or by you

A **principal** is a user or service identity. Its **object ID** identifies
that identity in the Entra directory; it is not an application's client ID.

| Variable | Description |
| --- | --- |
| `AZURE_ENV_NAME` | Environment name. Set by `azd env new`. Used to derive resource names. |
| `AZURE_LOCATION` | Primary Azure region. Set it before provision so the first-run hook can create the additional resource groups. |
| `AZURE_PRINCIPAL_ID` | Deployment identity's object ID for service setup and access. azd resolves it for Bicep; Terraform preprovision detects a missing value for ordinary CLI, service-principal and managed-identity authentication. |

For certificate, OIDC or custom managed-identity authentication, explicitly
set `AZURE_PRINCIPAL_ID` and `AZURE_PRINCIPAL_TYPE` to identify the caller.
These inputs are not credentials; use the caller's object ID, not its client
ID. See [Terraform authentication](deploy-terraform-infra-only.md#step-2-authenticate-and-select-the-target).

#### Application Cosmos DB

The default [application layout](application.md#default-deployment)
does not create application Cosmos DB resources or their dedicated identity.
Foundry backing storage is independent. Application composition enables Cosmos DB
for classic orchestration, administrative-panel metadata, a preserved classic
runtime, or a custom component declaring the `conversation-store` capability.
Setting `DEPLOY_COSMOS_DB=false` explicitly conflicts with those consumers and
stops provisioning with an explanation. Otherwise, leave the input unset to
follow the selected application's requirements.

For an additional application storage requirement, opt in before provisioning:

```bash
azd env set DEPLOY_COSMOS_DB true
```

Direct foundation-template deployments also default `deployCosmosDb` to `false`;
set it to `true` when application storage is needed. For an existing deployment,
review the provision preview and retain the account until its consumers and
data-retention requirements have been reviewed.

| Variable | Fresh-environment default | Description |

| Selection | Effect |
| --- | --- |

### Search region and quota

`AZURE_SEARCH_LOCATION` resolves the effective Bicep `searchServiceLocation`.
An unset or empty value falls back to `AZURE_LOCATION`. Both newly created
Search services use this effective region. Provider availability and Search
quota checks use that same region, not the primary region when an override
is set.

Search quota must cover the complete enabled service count: one Agent Application service
when `deploySearchService` (`DEPLOY_SEARCH_SERVICE`) is enabled, plus one Foundry
Search service when `deployAiFoundry` and `deployAAfAgentSvc`
(`DEPLOY_AAF_AGENT_SVC`) are enabled and `aiSearchResourceId` is not supplied.

When both creation paths are enabled, the check requires quota for two services.
Reusing a Foundry Search resource does not request a new service for that path.
Bypassing preflight does not resolve region mismatches or insufficient quota.
See [Search preflight region and quota](troubleshooting.md#search-preflight-region-and-quota).

### Additional native source identities

Enable each source with its compatible API contract, name and bindings.
Incomplete enabled sources fail before resource changes instead of
disappearing from a mixed knowledge base. The functional source guides
own those compatibility requirements.

These optional identity inputs are nonsecret UUIDs. Explicit deployment
environment values are published under `agent-lz`; omission invents no identity
and an explicit empty value clears that setting.

| Setting | Meaning |
| --- | --- |
| `WORK_IQ_APPLICATION_ID` | Work IQ app's application/client ID. |
| `WORK_IQ_FEDERATED_CREDENTIAL_ID` | Object ID of the credential that trusts the Search principal, not the principal ID. |
| `WORK_IQ_TENANT_ID` | App tenant ID for cross-tenant Work IQ configuration. |

### Explicit shared-source permission options

`FOUNDRY_IQ_INGESTION_PERMISSION_OPTIONS` defaults to `["rbacScope"]` when
omitted or actually null. An explicit JSON `[]` has a different meaning:
it can opt a supported active non-ADLS native Blob source into shared-source
metadata. Invalid input and unsupported active combinations fail closed.

This is not a permission grant or a repair for authentication/private-link
failures. Follow the [shared-source permission contract](foundry-iq.md#shared-source-permission-metadata)
for source constraints, audience review, allow/deny acceptance and recovery.

### Protected download configuration

Downloads reuse provisioned storage and Search bindings. There is no separate
permission-bypass input. Use [protected citation downloads](application-auth.md#protected-citation-downloads)
for runtime settings, consent and source-access requirements.

### Firewall SKU and management networking

New isolated standalone deployments select `AZURE_FIREWALL_SKU=Basic`.
Select `Standard` explicitly when DNS proxy, network-rule FQDN filtering or
greater capacity is required. Basic supports application HTTP(S) FQDN rules
and IP/service-tag network rules; assess its approximately 250 Mbps capacity
class against build, image-download and ingestion peaks.

| Topology | Local firewall data subnet/IP | Local management subnet/IP | GatewaySubnet |
| --- | --- | --- | --- |
| Standalone Basic | Required | Required | Explicit reservation only |
| Standalone Standard | Required | None | Explicit reservation only |
| External hub, with or without gateway | No IP; data subnet only if explicitly reserved | None | Explicit local reservation only |
| Public/non-isolated | None | None | None |

Both local SKUs use `AzureFirewallSubnet`. Basic additionally needs the
exact name `AzureFirewallManagementSubnet`, a /26-or-larger range and a
separate Standard/static public IP and management NIC configuration.
Keep management networking free of generic NSGs, workload default routes,
NAT, delegations and service endpoints. Validate externally managed subnet
routing with the network owner. Workload routes use the data-plane private IP.

For external hub egress, explicitly disable local firewall deployment and
configure the approved external next hop or route table. A deployment-mode
label alone does not configure egress or change hub resources.

### Opt-in firewall DNS proxy

`ENABLE_FIREWALL_DNS_PROXY` defaults to `false` and maps to the Bicep boolean
`enableFirewallDnsProxy` (also default `false`), which sets
`dnsSettings.enableProxy` on a `Standard` firewall. Basic with proxy enabled
is rejected; its policy omits DNS settings. It applies only when the
`deployAzureFirewall` and `networkIsolation` gates enable firewall deployment.
It is intended for a topology that deliberately uses the firewall as its DNS
forwarding path. The matching deployment guide applies the selection through
normal provisioning.

Enabling the proxy does
**not** redirect VNet or VPN clients to the firewall or rewrite their DNS
configuration. It is independent of the build-feed egress allowlist.

Client DNS routing and private-zone resolution remain separate requirements.
A proxy cannot repair missing zone links, VPN routes or application
authentication. Disabling it requires confirmation that the deployed DNS path
does not depend on it before reprovisioning.

### Subnet creation and addressing

Choose [subnet ownership](network-isolation.md#allocate-subnets-and-agree-ownership) first.
The global `DEPLOY_SUBNETS` switch defaults to `true`. Firewall data and
management switches default to `null` (auto): data follows the local isolated
firewall requirement, while management is used only by standalone Basic.
`DEPLOY_GATEWAY_SUBNET` defaults to `false`; explicitly enable it to reserve a
subnet for a separately configured local gateway. Other individual subnet
switches default to `true`. Creation also requires network isolation and the
global switch; management additionally requires an active standalone Basic
firewall, even when its creation switch is explicitly true.

| `deployDevopsBuildAgentsSubnet` | `DEPLOY_DEVOPS_BUILD_AGENTS_SUBNET` | Build agents |

A `false` creation flag means do not create/manage that subnet; it does **not**
disable its consumer. Every enabled consumer must have an existing, valid
subnet in the selected VNet, or be explicitly disabled. No consumer is silently
disabled or redirected to another subnet.

For a fresh deployment without Power Platform integration, omit its optional
reservation with `azd env set DEPLOY_POWER_PLATFORM_SUBNET false`.
In contrast, disabling application PE subnet creation still requires an
existing [application PE subnet](#application-private-endpoint-subnet)
when application private endpoints are enabled.

An isolated new VNet is still created when subnet creation is disabled, but
configuration fails if an enabled workload requires a subnet that is absent.
For an existing VNet, only selected subnets are created/updated, through
serialized child deployments; its entire subnet collection is not replaced.
Managed BYO subnet writes require `deployNsgs=true`; opting out of a subnet's
creation does not remove its existing NSG association. Creation flags are not
deletion commands or a guarantee of preserving every previously submitted
subnet in a deployment-owned VNet; Azure can reject removal of occupied subnets.

`deployAiFoundrySubnet` controls the Foundry Agent Service subnet association,
not subnet creation. Use `deployAgentSubnet` for creation ownership.

#### Network selection examples

For a new isolated environment, set `azd env set NETWORK_ISOLATION true`,
then apply the matching selection.

```bash
azd env set USE_EXISTING_VNET false
```

configure peering, DNS forwarding or runner connectivity.

##### Subnet delegations

- **Foundry Agent Service and Container Apps environment:**
  `Microsoft.App/environments`.
- **Power Platform:** `Microsoft.PowerPlatform/enterprisePolicies`.
- **AI Gateway:** `Microsoft.Web/serverFarms`.
- **All other subnets in this plan:** no delegation.

Firewall data subnet creation defaults to the local firewall requirement.
The management subnet is used only by a standalone Basic firewall.
GatewaySubnet is opt-in. The table is an address plan, not an unconditional
resource inventory; shared-hub services do not require these reservations
in the spoke.

With isolation off, no VNet or subnets are provisioned.

**Prepared subnets are not deployed services.** These reservations do not deploy
APIM or VPN/ExpressRoute gateways, create a Power Platform enterprise policy,
or associate a Power Platform environment. Those integrations need separate setup.

See the [application private endpoint subnet](#application-private-endpoint-subnet)
for its consumers and required separation from Foundry/grounding endpoints.

Keep the reserved name `GatewaySubnet`; do not attach an NSG, default-route
UDR or delegation to it. AI Gateway uses APIM Standard v2/Premium v2 outbound
VNet integration, with a subnet of `/27` or larger, delegated to
`Microsoft.Web/serverFarms` and associated with an NSG. Preserve an outbound
HTTPS path to Azure Key Vault. No reserved subnet name is required for APIM;
do not place APIM private endpoints in its delegated integration subnet.

The Power Platform `/24` is a capacity default, not a platform minimum.
Size for environment demand: approximately 25–30 IPs per production
environment or 6–10 per nonproduction environment, plus five subnet-reserved IPs.
See [Power Platform subnet sizing](https://learn.microsoft.com/power-platform/admin/vnet-support-overview#estimating-subnet-size-for-power-platform-environments).

## Outbound access

Running components declare destinations through
[`components[].egress`](build-your-own-app.md#runtime-egress-declarations).
The selected workloads determine the plan, including optional and additive
components. Build-package access is [separate](#application-specific-package-feeds).
Neither replaces private endpoints, DNS, routes or authorization.

For example, the supplied orchestrator and ingestion declare
`openaipublic.blob.core.windows.net` over HTTPS/443 for cold-cache tokenizer
initialization. The UI has no additional fixed destination. Configured
SharePoint, SQL, MCP and other custom destinations need their own review.

### Policy ownership

| Deployment | Behavior |
| --- | --- |
| `NETWORK_ISOLATION=false` | No component firewall reads or writes; declarations do not create a firewall |
| Isolated with a deployment-managed firewall | Reconciles only marked application rules in `AgentLzComponentEgress`, priority 400 |
| Isolated with an external firewall | Reports required rules and components without egress declarations; never reads or mutates the external policy |

For managed policies, the runner needs management-plane subnet reads and
`Microsoft.Network/firewallPolicies/ruleCollectionGroups/read` and `write`
on the deployment policy. The reconciler does not write the parent policy.
For external policies, the network owner compares the report with their own
policy and applies approved changes. Reporting does not prove that egress is
allowed.

Shared destination/protocol/port tuples produce one rule, with sources and
ownership combined across components. Removing one owner narrows sources where
possible; the rule remains until its final declared owner disappears.

Enabled components without declarations retain their owned requirements.
Other rules and collections, including unmarked entries inside
the component group, are preserved. Ownership collisions, malformed marked
rules, conflicting priorities or concurrent changes fail rather than being
silently adopted or overwritten.

### Source scope and saved plans

Rules use actual provisioned Container Apps or Foundry agent subnet prefixes,
including existing-VNet selections, not the whole VNet or `*`.
Every workload sharing a source subnet can use its union of destinations.
Existing platform rules can also permit traffic. Subnet scope is not
component isolation.

Preprovision saves the reviewed declaration plan at
`.azure/<environment-name>/component-egress-plan.json`.
Postprovision and predeploy resolve actual prefixes and print the plan before
managed reconciliation. Deferring postprovision defers its reconciliation,
not the predeploy connectivity and plan checks.

A missing or stale saved plan stops apply before Azure access. Do not copy
plans or outputs between environments. Use the
[review procedure](deploy-infra-only.md#review-component-egress) for local and
resolved read-only reports, and [rollback](deploy-full-stack.md#outbound-rule-recovery)
for rule removal before reverting hooks.

## Deployment controls

Hook execution and application selection use the variables below.
The selected application also affects the resource footprint.

| Variable | Description |
| --- | --- |
| `BUILD_MODE` | `local` uses Docker on the deployment host. `acr-task` uses Azure Container Registry. Unset values select a mode as described below. |
| `RUN_FROM_JUMPBOX` | `false`, `0`, `no` or `skip` defers isolated post-provision. A truthy value requests private connectivity checks, even when the warning flag is set. It does not provide connectivity. |
| `AZURE_SKIP_NETWORK_ISOLATION_WARNING` | `true` defers isolated post-provision configuration unless `RUN_FROM_JUMPBOX` explicitly requests a connectivity check. |
| `PREFLIGHT_SKIP` | `true` skips regional and infrastructure preflight checks, not application-definition or topology validation. |

| `AGENTLZ_APP_DEFINITION` | Path to a custom application definition. See [Custom applications](build-your-own-app.md). |

Preflight skip flags are diagnostic controls, not a supported fix for quota,
region, permission or network failures.

An explicit `BUILD_MODE` takes precedence. When it is unset, component scripts
first apply recognized `USE_DOCKER` values: `true`, `1` or `yes` select local;
`false`, `0` or `no` select ACR Tasks. Without either override, network
isolation or a configured task pool selects ACR Tasks. Otherwise, usable Docker
selects local and unavailable Docker selects ACR Tasks. Explicit `local`
fails if Docker is unusable rather than falling back silently.

### Private image builds

The isolated remote build path requires a VNet ACR Task agent pool.
`DEPLOY_ACR_TASK_AGENT_POOL` creates that pool only with isolation enabled.
It does not connect the deployment host or grant it build permissions.

Hosted orchestrator image preparation always uses ACR Tasks.
`BUILD_MODE=local` does not change that preparation path or the isolated
custom source-build path. See
[Hosted agents](hosted-agents.md) and
[Custom applications](build-your-own-app.md#source-pinning).

For components that support local Docker, a VNet-connected Docker host is an
alternative. Hosted image preparation and isolated custom source builds still
need the private pool unless an already-built immutable digest avoids the build.
Without a pool, the root predeploy guard additionally requires `BUILD_MODE=local`,
and every remaining service must support that choice.
See [pool diagnostics](troubleshooting.md#acr-task-agent-pool-is-missing).

### Application-specific package feeds

The root deployment defaults include dependency-verified package feed
destinations alongside common language and OS package registries, through
the scoped infrastructure build-egress configuration. This is a build-only
allowlist, not a runtime or general Internet exception. It does not allow
every mirror recorded in a custom application's lockfile. The exact component
commit's `resolved` URLs and download redirects determine its build needs.

Additional dependencies are declared in
`parameters.additionalAcrTaskBuildFqdns.value` in the root `main.parameters.json`.
This is an explicit array, not an `azd` environment variable. Provisioning
applies it; the connected runner needs the same reviewed parameter file to
preserve the setting on later provisions.

The Agent Application orchestrator frontend lockfile uses
`ms-feed-2.pkgs.visualstudio.com`, `ms-feed-12.pkgs.visualstudio.com`,
`ms-feed-17.pkgs.visualstudio.com`, and `ms-feed-25.pkgs.visualstudio.com`.
Their public package downloads redirect to `*.vsblob.vsassets.io`.
These four exact feeds and the redirect content delivery network (CDN) are included in the Agent Landing
Zone default build allowlist. `packages.microsoft.com` is already included in
the OS-package rule and does not need an additional entry.

With `extendFirewallForAcrTaskBuilds=true` (the default) and an effective ACR
Task agent pool, the feeds, redirect CDN, and additional hosts are allowed only
from the build-agent subnet over HTTPS on port 443. They are not added to
jumpbox, application, or agent-subnet rules. The additional-host array defaults
to empty.

Disabling the build-egress extension removes these package rules.
Re-enabling it restores them. This egress rule has no DNS-proxy dependency and
does not change client DNS.

Do not enable public registry access, allow all Internet egress, disable TLS
verification, or change dependency integrity hashes to work around a failed build.

See [Package installation fails inside the build pool](troubleshooting.md#package-installation-fails-inside-the-build-pool)
for diagnosis.

| `RETRIEVAL_AUTH_MODE` | Platform-published `native_search` authorization contract, not an operator permission bypass. See [delegated retrieval](foundry-iq.md#delegated-native-retrieval). |
| `KEY_VAULT_URI` | Infrastructure output for the deployed vault, empty when absent. Use the actual URI for bootstrap rather than constructing a cloud DNS suffix. |
| Local binding records | Preserve the original application, provider, group and backend bindings for updates, recovery and removal. Refreshing outputs does not recreate immutable bindings. |

### Search shared private links

For isolated native Blob setup, infrastructure publishes
`SEARCH_SHARED_PRIVATE_LINKS` as a JSON array under `agent-lz`.
Each entry records the owned `name`, `groupId` and `privateLinkResourceId`.
It is generated metadata, not an operator override or runtime retrieval setting.

Configuration verifies the exact Search links, target IDs and groups before
dependent mutation and native source creation. The gate applies to isolated
`foundry_iq` native `azureBlob` sources, not `searchIndex` or inactive native
ingestion. It covers the application Search links to document Blob storage
(`blob`) and the deployment Foundry account (`openai_account`,
`foundry_account`, `cognitiveservices_account`), not the separate Foundry
Search service or unrelated links.

The source-side GET must match the declared name, target and group, and its
resource ID when present. Each link must be `Approved` and `Succeeded`.
Target private endpoint connection requests need an authorized administrator's
approval. The workflow never approves them automatically.

Target requests can have opaque or paginated identifiers. Administrators must
identify the correct request using the
[shared-link approval procedure](https://learn.microsoft.com/en-us/azure/search/search-indexer-howto-access-private).
The runner reuses its existing Azure credential and needs Search shared-link
read access, not target connection write access or a new secret.
Source readiness does not require the runner to read opaque target requests.
See [private-link diagnostics](troubleshooting.md#search-shared-private-links-are-not-ready)
for pending approval, propagation, timeouts and retry.

## Configuration publication

Use [Application settings](application-settings.md) for runtime configuration
tasks and effective-value checks. [Conversations & files](conversations.md)
covers continuity settings. The declarations below describe how deployment
publishes and owns those values.

Post-provision publishes runtime settings to Azure App Configuration with
the label `agent-lz`. That is the label for platform-owned settings.
Reprovisioning is not application publication and must preserve the images
and revisions managed by the application deployment workflow.

### Configuration ownership and declarations

Terraform manages foundation connections, model metadata and input-driven
settings. Shared postprovision queries existing key names, not values, and
seeds **only missing defaults**, preserving existing values, content types
and Key Vault-reference metadata.

`config.deployment.appconfig` updates runtime-owned keys according to the
product's single ownership inventory. Its intent comes from the declared
parameter document and selected azd environment. Declare additional entries
through root `parameters.additionalAppConfigurationSettings.value`, using
`name` and string `value`, plus optional `label` and `contentType`.
Declared labels, content types and literal values are preserved.

Keep the exact reviewed declaration, including required private inputs, on
every runner. A missing required declaration fails; outputs and Terraform state
are not substitutes. The publisher's optional `--input <path>` selects that
exact parameter document. Do not create per-key azd variables to transport it.

Routing, identity and other authority-controlled conflicts are rejected.
Unsupported runtime Key Vault-reference overrides fail explicitly; use the
existing governance or continuity owner for those references.

### Effective settings

Change foundation-owned settings in their declared inputs and runtime-owned
settings through their publisher; a missing-only default seed does not make
every key operator-owned. Custom application
definitions validate settings but do not publish them; the application
must publish its own runtime settings.

An accepted write is not evidence that a running process loaded the value.
Use [effective-value checks](application-settings.md#overrides-and-effective-values)
for precedence and reload behavior.

The [Deploy full stack](deploy-full-stack.md#change-a-runtime-setting)
guide provides commands, including [secret rotation](deploy-full-stack.md#rotate-a-secret) for
versioned versus unversioned Key Vault references. Changing deployment selection,
RBAC or infrastructure requires the matching full workflow, not just a key edit.
